# 介護施設 家族連絡アプリ Constitution

## Core Principles

### I. 家族が日々の様子と「知りたいこと」を、聞かずに・遠慮せずに知れることを最優先する

- 家族は頼まなくても、施設が開示した日々の様子を連絡帳で MUST 見られる。
- 家族は知りたいことを、自由記述ではなくテーマのボタンで選んで、施設（介護職員）に
  MUST 頼める。頼んだことが施設に届いたことが、家族に MUST 分かる。
- 頼んだことへの職員の返事が届いているときは、家族向け画面のファーストビュー
  （アプリを開いて最初に見える領域）にまだ読んでいない返事を MUST 表示する。
- 情報がまだ記録されていない場合は「まだ記録されていません」と MUST 明示し、
  空欄や推測で埋めてはならない。
- 新機能は「家族が施設に電話しなくて済む場面が増えるか」を判断基準として MUST 説明する。

**理由**: 講師レビューで示された核心。家族（佐藤さん）は施設に遠慮して聞けない。
頼まなくても日々の様子が分かり、それでも聞きたいことは、聞いて帰ってくる一往復の手間を
ボタン 1 つの頼みごとと連絡帳の返事に置き換えることが、このアプリの存在価値である。

### II. 職員の入力負担を増やさない

- 職員の記録入力は、ボタン・選択式を基本とし、自由記述を必須項目に MUST NOT する。
- 家族向けの連絡帳は、職員がお世話の場で入力した記録から MUST 自動で作る。
  家族のために職員が追加で入力するものは、頼みごとへの返事や写真（H）など、
  ボタン・定型文・撮影だけで短時間にできるものに MUST 限る（自由記述は任意の書き足しに限る）。
- 1 項目の記録（例: 1 食分の食事量）は、タブレットで 3 タップ以内・10 秒以内を目標に
  SHOULD 設計する。これを超える設計は plan で理由を MUST 記載する。
- 家族からの問い合わせが職員に直接割り込む（ケア中に呼ばれる）経路を新たに作っては
  MUST NOT。家族の頼みごと・メッセージは、職員への通知・音で知らせず、職員がアプリの画面を開いたときに見せる。
  人の対応が必要なものは、AI が質問の種類（医療・お金・苦情など）を付けて施設の職員が見られる形で MUST 渡し、
  だれが対応するかは職員が決める（AI は担当を決めない）。苦情は、生活相談員と施設長だけが見られる形に MUST する。
- 外国人職員が母国語で入力できる手段を、日本語入力より手間が増えない形で SHOULD 用意する。

**理由**: 施設が導入する条件は「手間が増えないこと」。田中さん（IT が苦手）や
シティさん（日本語の記録に時間がかかる）の負担が増えれば、記録の質も導入も崩れる。

### III. AI は医療判断をせず、記録にないことは答えず、人につなぐ (NON-NEGOTIABLE)

- AI は診断・病状の評価・服薬や治療の助言など医療的な判断を MUST NOT 行う。
  該当する質問は、定型文で人（生活相談員・看護職員）につなぐ。
- AI の回答・要約・整文は、施設の記録に根拠がある内容に MUST 限定する。
  記録にないことは「記録にありません」と答え、推測で補ってはならない。
- AI が生成・加工した文章は、どの記録にもとづくかを MUST 追跡できる。
- 翻訳・整文した記録は、次の順を経てからでなければ家族に MUST NOT 届けない:
  1. 整えた日本語を本人の母国語に訳し戻し、記録した職員本人が内容を確認する
  2. リーダー（または指定職員）が承認する
  3. 承認後に家族向けの連絡帳へ反映する
- 緊急性のある内容（急変・事故など）は AI やアプリ内表示だけで完結させず、
  人が電話等で連絡する運用を MUST 前提とする。

**理由**: 介護の現場で誤った医療情報や記録にない推測が家族に届くと、信頼と安全を損なう。
AI は「伝える手間を減らす」道具であり、判断の主体にはしない。

### IV. 家族に何を開示するかは施設が選ぶ

- 家族に見せる記録項目は、施設が項目単位で MUST 選択・変更できる。
- 施設が開示していない項目は、家族向けの画面・連絡帳・AI の回答・通知のいずれにも
  MUST NOT 出さない（AI が非開示項目を根拠に答えることも禁止）。
- 家族が「知りたいこと」として選べる選択肢は、施設が開示している項目・テーマの範囲に MUST 限る。
- 家族アカウントは、自分の家族（紐づいた入居者）の情報以外に MUST NOT アクセスできない。
- 開示設定の変更は、いつ・誰が変えたかを MUST 記録する。

**理由**: 記録の扱いは施設の責任範囲であり、施設の安心がなければ導入されない。
個人情報（要配慮個人情報を含む）を扱うため、見せる範囲の決定権を施設側に置く。

### V. 10 日間で「動くもの」を優先する

- 開発期間は SEC10・11 の 10 日間（平日）。各スプリント（月火／水〜金）の終わりに、
  デモできる状態の縦切り機能を MUST 1 つ以上残す。
- 各ユーザーストーリーは単独でデモ・検証できる単位に MUST 切る（spec の優先度 P1→P2→P3）。
- スコープ外の機能（立替金の精算、逆・連絡帳、話すだけで記録、聞き書き AI、
  難しい質問の下準備、入居前ヒアリング支援 AI）は、spec・plan・tasks に MUST NOT 含めない。
  追加する場合は本 Constitution の改定を先に行う。
- 外部連携（SMS、介護記録システム連携など）はモックやスタブで SHOULD 代替し、
  本番接続はデモに不可欠な場合だけにする。ただし決済（J）は課題要件のため
  決済サービス（Stripe など）のテストモードで実際に MUST 組み込む（実課金はしない）。
- 新しいライブラリ・サービスの導入は、10 日間で使いこなせる根拠を plan に MUST 書く。
- 課題要件の MUST の機能（F 問い合わせ AI エージェント・J 決済）は、スプリント順にかかわらず
  1 週目のうちに最小限の版を MUST 動かす。

**理由**: 講師に提出・発表するのは「動くもの」。完成度の高い一部機能は、
未完成の全機能より価値が伝わる。

## 共通の設計制約

- **UI 方針（全画面共通）**: 絵文字とアイコンを併用する。日本語はひらがな中心にせず、
  日本人が読んでも違和感のない「やさしい日本語」で漢字を使う。ボタン・見出し・案内文などの
  固定の文言は、すべての漢字の上にふりがなを MUST 付ける。利用者が自由に入力した文は対象外とする。
  ただし、施設の申し込みの画面（申し込み・完了）は、ふりがなを付けない（例外）。
  ふりがなは、外国人職員にも読みやすくすることが主な目的で、申し込みの操作者の施設長は、
  日本人か、日本語を読める外国人と考えられると、チームの話し合いで判断したため。
  申し込み以外の画面（ログイン画面を含む）は、MUST のままとする。
  主要ボタンは日本語に加えて多言語（少なくともインドネシア語・英語）で表示を切り替えられる。
  訳して表示するときは、ふりがなを付けない。
  家族向け画面は 50 代の会社員が昼休みのスマートフォンで短時間に読める量に収める。
- **利用者と権限**: 家族 / 介護職員 / リーダー（承認者）/ 生活相談員 / 事務員 / 施設長 /
  システム管理者（アプリ会社）を区別し、各機能は必要な役割にだけ MUST 開放する。
- **個人情報**: 入居者の記録・写真は要配慮個人情報として扱い、通信は暗号化する。
  デモ・開発では実在の人物のデータを MUST NOT 使わず、架空データを用いる。
- **施設の前提**: 入居者最大 30 人、職員 16 人（うち外国人 3 人）、面会 10〜17 時・
  1 日 2 家族まで・1 組 1 時間 30 分、事務所 9〜18 時。これを超える規模対応は対象外とする。
- **記録媒体**: アプリで扱うのは連絡帳（介護職員がお世話の場でタブレットからボタン入力する一次メモ）とする。
  施設全体の日報（その日のスケジュール）と入居者ごとの介護記録は、施設の既存の方法のままとし、
  アプリに取り込まず家族にも見せない（spec 001 で決定）。

### 課題要件（講師指定・必須）

技術スタックはチームで自由に選んでよいが、次を MUST 満たす。plan の Constitution Check で
毎回確認する。

- **構成**: Web アプリケーションを基本とし、フロントエンドとバックエンドを分離する
  （`frontend/` と `backend/`）。ネイティブアプリは +α として作ってもよい。
- **コンテナ**: 開発・本番ともコンテナで動かす。
- **キャッシュ**: キャッシュサーバー（Redis または Memcached）を利用する。
  何をキャッシュするか（例: 家族の連絡帳の組み立て結果、セッション）は plan で決め、
  開示設定（原則 IV）を変えたときに古いキャッシュで非開示項目が出ないようにする。
- **AI Agent**: AI Agent の技術要素を含める（主に F 問い合わせ AI エージェント。
  原則 III に従う）。
- **決済**: Stripe などの決済機能を組み込む（J システム利用料。テストモードでよい）。
- **セキュリティ**: XSS・SQL インジェクションなどの対策を行う。利用者の入力は表示時に
  エスケープし、データベースへの問い合わせはパラメータ化する。
- **テスト**: 単体テストはテストコードを書く。結合・総合テストは
  `docs/テスト設計書.md` にテスト設計とテストシナリオを作って実施する。
  各 spec の受け入れシナリオ（Given/When/Then）をテストシナリオの元にする。
- **ログ**: 開発環境と本番環境でログの出し方を分ける（例: 開発は詳細ログ、
  本番は必要なレベルだけを構造化して出し、個人情報はログに出さない）。

### 課題要件（ADVANCE・できれば対応）

- 本番環境にデプロイする。サブドメインを取得し、https でアクセスできるようにする。
- フロントエンドのテストを自動化する。
- プロンプトインジェクションに留意する。家族の質問・職員の記録など利用者の入力は、
  AI に対する命令ではなくデータとして扱い、AI が参照できる記録を
  その家族に開示された範囲（原則 IV）に限定したうえで渡す。
  ADVANCE ではあるが、AI Agent を家族に公開する場合は原則 III・IV を守るため MUST とする。

ADVANCE の項目は、スプリント 1〜3 の機能がデモできる状態になったあとに
取り組む（原則 V）。ただし、コンテナ・ログの出し分け・https は後から足すと手戻りが大きいため、
本番デプロイの準備はスプリント 1 から SHOULD 並行して進める。

## 開発の進め方

- 機能ごとに SpecKit の流れ（specify → clarify → plan → tasks → implement）で進める。
  plan の「Constitution Check」で原則 I〜V への適合を MUST 確認し、違反がある場合は
  Complexity Tracking に理由を書く。
- spec には、どのペルソナのどの困りごとを解決するかを MUST 書く
  （佐藤さん / 田中さん / シティさん / 山本さん / 佐々木さん / 猪熊さん）。
- スプリント順の基本は 1: C→B→A（記録 → 開示 → 家族が知りたいことを頼み、返事を見る）、
  2: D・G・H、3: F・E・J。ただし F・J は原則 V のとおり 1 週目のうちに最小限の版を動かす。
  順序の変更はチームで合意し、マイルストーンに記録する。
- 講師提出物（README のイシュー・ソリューション、PRD の背景・目的・対象ユーザー・
  ユーザーストーリー）は spec の内容と食い違わないよう SHOULD 同期する。

### 記録のルール（フローとストック）

- 決まったことは MUST リポジトリに記録する。Discord は連絡・相談（フロー）に使い、
  Discord にしかない決定は「決まっていない」ものとして扱う。
- **フロー**（その時点の記録・時系列）: `docs/context/` の議事録（meeting）・
  デイリースクラム（daily-scram）・スプリント（sprint）。日付つきで追記し、書き換えない。
- **ストック**（いつ見ても最新の正）: `README.md`、`docs/*.md`（PRD・要件定義・設計書）、
  `specs/<機能>/`、本 Constitution。議事録で決まったことは、その週のうちに該当する
  ストック文書へ MUST 反映し、議事録には反映先を書く。
- 同じ内容を 2 か所で管理しない。機能単位の詳細は `specs/<機能>/`（spec・plan・
  data-model・contracts・tasks）を正とし、`docs/` の設計書は全体像（一覧・図）と
  各 specs へのリンクを持つ。
- タスクは `specs/<機能>/tasks.md` を元にタスク管理ツールへ起こし、担当者・状態を管理する。

### 体制と意思決定

- リーダーと領域ごとの責任者（例: フロントエンド・バックエンド・インフラ／デプロイ・
  AI・テスト・ドキュメント）を MUST 決めて README に記載する。
- 領域の中のことは責任者が決め、領域をまたぐこと・スコープ・本 Constitution の改定は
  チームの会議で決める。会議で決まらないときはリーダーが決める。
- 決定は議事録に「決定事項」として残す（上記の記録のルールに従う）。

## Governance

- 本 Constitution は、このリポジトリの他のドキュメント・慣習より優先する。
- 改定はチームメンバーへの共有と合意を経て行い、Sync Impact Report を付ける。
- バージョンはセマンティックバージョニングに従う:
  MAJOR = 原則の削除・意味の変更、MINOR = 原則・節の追加や大きな拡充、
  PATCH = 文言の明確化・誤字修正。
- spec・plan・tasks のレビュー時に本 Constitution への適合を確認する。
  原則 III（AI と医療判断）は例外を認めない。
