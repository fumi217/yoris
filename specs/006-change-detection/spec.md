# Feature Specification: 記録から入居者のいつもと違う様子に気づき、職員に知らせる（E：変化の検知）

**Feature Branch**: `docs/spec-006-change-detection`

**Created**: 2026-10-21

**Status**: Draft

**Input**: User description: "E：変化の検知（spec 006、短い名前 change-detection）。連絡帳の記録（食事量・機嫌・様子・眠り、様子のメモ）から、入居者のいつもと違う様子（例：食事量が 2 食続けて少し以下、元気がない日が続く）に気づき、職員に知らせる。職員向けの機能で、ケアを中断させない（通知・音を出さない）。医療の判断はしない。"

## 背景と解決する困りごと

| ペルソナ | 困りごと | この機能で変わること |
|---|---|---|
| 田中健太・シティさん（介護職員） | シフト制で、前の勤務の人の記録まで見返す時間がない。「昨日も食べていなかった」に気づきにくい | 職員のアプリを開くと、いつもと違う様子の入居者が一覧の上に目印つきで出る。何が、いつからか分かる |
| 山本由美（生活相談員） | 入居者の小さな変化を、家族から聞かれて初めて知ることがある | 変化に早く気づけるので、必要なら看護職員に確かめたり、家族に電話したりできる |
| 佐藤美紀（家族） | 母の様子の変化を、施設が気づいているのか分からない | （直接は見ない）施設が変化に早く気づき、必要なときは電話で知らせてもらえる |

spec 001 では「食事量が 2 食続けて『少し（2割）』以下だった場合 → スプリント 1 では家族への特別な通知は行わない（変化の検知・通知は E で扱う）」としていた。
この機能は、**職員が気づくための目印**で、医療の判断はしない（Constitution 原則 III）。家族への緊急の連絡は、これまでどおり人が電話で行う。

## Clarifications

### Session 2026-10-21

- Q: 目印の決まりに、AI で文を読むものも入れるか？ → A: 入れない。決まった条件（記録の値で判断する）だけにする。目印が付いた理由がはっきりし、テストで確かめやすく、AI が医療の判断に近づくことも避けられるため
- Q: 目印を見られるのは、どの職員か？ → A: 介護職員・リーダー・生活相談員・施設長。事務員は除く（体調に関わる情報を、お世話に関わる職員だけに見せるため）
- Q: 目印が付いたことを、家族にも知らせるか？ → A: 知らせない。施設の職員が気づくための機能に留め、家族への連絡が要るときは人が電話する（Constitution 原則 III）
- Q: 食事量の決まりで、おやつも 1 食として数えるか？ → A: 数えない。朝ごはん・昼ごはん・夜ごはんだけで数える（おやつを入れると目印が増えすぎ、職員が見なくなるため）
- Q: 記録がない日（未記録）をはさんだときも「続けて」と数えるか？ → A: 短いあいだだけ飛ばす。食事は 1 食、機嫌・眠りは 1 日までの未記録なら飛ばして数える。それより長くあいたら数え直す（未記録を「食べていない」などとは数えない）
- Q: 目印をまとめて見られる画面を作るか？ → A: 作らない。入居者一覧の上に「確かめていない目印：◯件」を出し、押すと、まだ確かめていない目印のある入居者だけに絞れる
- Q: 目印が付いたら、生活相談員にも自動で知らせるか？ → A: 知らせない。相談員も、介護職員と同じ入居者一覧の件数で目印を見る（別の仕組みは足さない）
- Q: 目印の履歴は、職員がどこで見返せるか？ → A: 入居者を開いた画面に、その入居者の過去の目印（付いた日・消えた日・当てはまった決まり・確かめた職員・ひとこと）を新しい順に並べる。施設全体の履歴の画面は作らない

### Session 2026-10-21（PR #40 のレビュー）

- Q: 記録を保存したときの調べ直しは、どこから呼ぶか？（PR #40 ゆう） → A: みさきが「この入居者の目印を調べ直す関数」（例：`evaluate_change_flags(session, resident_id)`）を作り、ゆうが記録の保存・修正・取り消しの処理（spec 001 の `services/records.py`、001-T026）の中から呼ぶ。
  spec 001 の `create_reply_notice` と同じく、同じ DB のセッションを渡し、関数の中では commit しない（記録と目印が同じトランザクションで確定し、記録だけ保存されて目印がずれる、ということが起きない）
- Q: 入居者一覧の目印・件数・絞り込みは、だれが作るか？（PR #40 ゆう） → A: ゆうの入居者一覧（spec 001 の 001-T028・001-T031）に足す。目印と「確かめていない目印」の件数を返す関数はみさきが用意し、ゆうが一覧から呼ぶ（#31・#38 と同じ形）。
  事務員は職員の画面（入居者一覧・記録の画面）を開けない（spec 001 の contracts のまま）ので、目印と件数も見えない（PR #45 ゆう。#40 の「事務員も開く」を直した）
- Q: 入居者一覧に出すもの（未記録・返事待ち・家族からのメッセージ・承認待ち・目印）の並べ方と置き場所は？（PR #40 ゆう） → A: ゆうが画面設計（docs/画面設計.md）を作るときに、まとめて決める

## User Scenarios & Testing *(mandatory)*

> E は作り込み（Day 5・10/28。作業分担MTG・docs/マイルストーン.md）の機能。最初に作るのは User Story 1。

### User Story 1 - 職員がアプリを開くと、いつもと違う様子の入居者に目印が付いている (Priority: P1)

職員（田中さん）は、職員のアプリの入居者一覧を開く。決めておいた決まり（例：食事量が 2 食続けて「少し（2割）」以下）に当てはまる入居者には、
目印（例：⚠️ いつもと違う様子）が付き、一覧の上のほうに出る。入居者を開くと、何がいつから当てはまっているか（例：「昨日の夜ごはんから 2 食続けて、少し以下」）が分かる。

**Why this priority**: シフトをまたいだ小さな変化に気づける、この機能の中心。記録（spec 001）があれば作れる。

**Independent Test**: 架空の入居者に、昨日の夜ごはん「少し（2割）」・今日の朝ごはん「食べていない」を記録し、職員で入居者一覧を開くと、その入居者に目印が付き、理由が表示されることを確かめる。

**Acceptance Scenarios**:

1. **Given** 入居者「佐藤さんの母」の食事量が、昨日の夜ごはん「少し（2割）」、今日の朝ごはん「食べていない（0割）」, **When** 職員が入居者一覧を開く,
   **Then** その入居者に「⚠️ いつもと違う様子」の目印が付き、一覧の上のほうに出る
2. **Given** 目印が付いている入居者, **When** 職員が入居者を開く,
   **Then** 「食事量：昨日の夜ごはんから 2 食続けて、少し以下」のように、当てはまった決まりと、もとになった記録（日付・食事区分・値）が表示される
3. **Given** 「食事なし（外泊・入院など）」の食事がある, **When** 決まりを調べる,
   **Then** 「食事なし」は「食べていない」として数えない（外泊・入院で目印が付かない）
3a. **Given** 昼ごはん「少し（2割）」のあと、おやつ「食べていない」, **When** 決まりを調べる,
   **Then** おやつは数えないので、目印は付かない（次の夜ごはんで決まる）
4. **Given** 目印が付いたあと、次の食事で「ほぼ全部（8割）」を記録した, **When** 職員が入居者一覧を開く,
   **Then** 決まりに当てはまらなくなったので、目印は消える（もとの目印は履歴に残る）
5. **Given** 目印が付いた, **When** 職員のタブレットを見る,
   **Then** 通知・音・画面を遮る表示は出ていない（アプリを開いたときに見える。Constitution 原則 II）
6. **Given** 目印の表示, **When** 職員が読む,
   **Then** 「病気の疑い」などの医療の判断や助言は書かれていない。そばに「気になるときは、看護職員・生活相談員に相談してください。急変は電話で」と案内がある

### User Story 2 - 職員が目印を確かめ、対応したことを残す (Priority: P2)

目印に気づいた職員は、入居者の様子を確かめ、「確かめた」を押して、ひとこと（例：「本人は元気。食欲が落ちているので夕食を様子見」）を残す。
次の勤務の職員は、同じ目印に誰がいつ何をしたかを見られる。

**Why this priority**: 目印が出るだけでは、同じことを何人もが確かめたり、誰も確かめなかったりする。引き継ぎのために要るが、US1 の目印があってからの機能。

**Independent Test**: 目印の付いた入居者を開いて「確かめた」とひとことを残すと、別の職員でログインしたときに、確かめた職員・日時・ひとことが見えることを確かめる。

**Acceptance Scenarios**:

1. **Given** 目印が付いている, **When** 職員が「確かめた」を押してひとこと（100 文字まで、任意）を書く,
   **Then** 目印は「確かめ済み」になり、確かめた職員・日時・ひとことが残る
1a. **Given** 3 人の入居者に、まだ確かめていない目印が付いている, **When** 職員が入居者一覧を開く,
   **Then** 一覧の上に「確かめていない目印：3 件」と表示され、押すとその 3 人だけに絞れる
2. **Given** 「確かめ済み」の目印, **When** 次の勤務の職員が入居者一覧を開く,
   **Then** 目印は「確かめ済み」と分かる形（色を変える など）で残り、誰がいつ確かめたかが見える
3. **Given** 「確かめ済み」のあと、さらに決まりに当てはまる記録が続いた（例：3 食続けて少し以下）, **When** 職員が入居者一覧を開く,
   **Then** 目印は「確かめ済み」から、まだ確かめていない状態に戻る
4. **Given** 先週、同じ入居者に目印が付いて消えていた, **When** 職員が入居者を開く,
   **Then** 過去の目印として、付いた日・消えた日・当てはまった決まり・確かめた職員・ひとことが新しい順に並んでいる

### User Story 3 - 施設が、どの変化に目印を付けるかを選ぶ (Priority: P3)

生活相談員・施設長は、管理画面で、目印を付ける決まりを選ぶ（オン／オフ）。決まりは、あらかじめ用意したものから選ぶ。

**Why this priority**: 施設や入居者によって、気にしたい変化が違う。ただ、最初は用意した決まりがそのまま動けば足りるので、最後に置く。

**Independent Test**: 管理画面で「眠り」の決まりをオフにすると、眠りの記録が続いても目印が付かないことを確かめる。

**Acceptance Scenarios**:

1. **Given** 管理画面, **When** 相談員が「変化の目印」の設定を開く,
   **Then** 用意された決まりの一覧と、それぞれのオン／オフが表示される（初期値はすべてオン）
2. **Given** 「眠り：2 日続けて、あまり眠れなかった」をオフにした, **When** 眠りの記録が 2 日続けて「あまり眠れなかった」,
   **Then** 目印は付かない
3. **Given** 設定を変えた, **When** 施設長が変更履歴を見る,
   **Then** いつ・誰が・どの決まりを変えたかが分かる

---

### Edge Cases

- 記録がない日（未記録）があった場合 → 未記録を「食べていない」などとは数えない（推測しない。原則 III）。食事は 1 食、機嫌・眠りは 1 日までの未記録なら飛ばして「続けて」と数え、
  それより長くあいたら数え直す（例：月曜「元気がない」、火曜は未記録、水曜「元気がない」→ 目印が付く。月曜「元気がない」、火〜木曜は未記録、金曜「元気がない」→ 付かない）。
- 記録が取り消された・押し直された場合 → 取り消し・修正のあとの記録で調べ直し、当てはまらなくなれば目印を消す。
- 入居者が入院などで何日も「食事なし」が続いた場合 → 目印は付けない（「食事なし」は数えない）。
- 目印の決まりに、施設が非開示にしている項目（例：眠り）が含まれる場合 → 職員向けの機能なので、非開示の項目も含めて調べる（家族には出さないので Constitution 原則 IV に反しない）。
- 同じ入居者に、複数の決まりが同時に当てはまった場合 → 目印は 1 つにまとめ、入居者を開くと当てはまった決まりがすべて並ぶ。
- 緊急を思わせる記録（例：様子のメモに「転倒」）があった場合 → この機能は緊急の連絡には使わない。書く画面と目印のそばに「急変・事故は、すぐに電話で」と案内する（原則 III・spec 001 FR-028）。
- 職員が目印を見ても何もしなかった場合 → 目印は残り続ける（自動で消さない）。催促の通知はしない。

## Requirements *(mandatory)*

### Functional Requirements

**目印を付ける（US1）**

- **FR-001**: System MUST 連絡帳の記録（spec 001 の食事量・機嫌・様子・眠り）が保存・修正・取り消されるたびに、その入居者が決まりに当てはまるかを調べ、目印を付ける・消す。
  調べ直しは、記録の保存・修正・取り消しと同じトランザクションの中で行い、記録と目印が食い違ったまま確定しないようにする。
- **FR-002**: System MUST 用意する決まりは次のとおりとする（どれも初期値はオン）。
  - 食事量：朝ごはん・昼ごはん・夜ごはんのうち、2 食続けて「少し（2割）」以下（「食べていない（0割）」を含む。「食事なし」とおやつは数えない）
  - 機嫌・様子：2 日続けて「元気がない」
  - 眠り：2 日続けて「あまり眠れなかった」
  決まりは、記録の値で判断する決まった条件だけとし、AI で文（様子のメモなど）を読んで判断するものは入れない。
  「続けて」は、食事は 1 食、機嫌・眠りは 1 日までの未記録なら飛ばして数え、それより長くあいたら数え直す。未記録は当てはまる値として数えない。
- **FR-003**: System MUST 目印の付いた入居者を、職員のアプリの入居者一覧の上のほうに、目印（「⚠️ いつもと違う様子」）つきで出す。入居者を開くと、当てはまった決まりと、もとになった記録（日付・項目・区分・値）を表示する。
  入居者一覧の上に「確かめていない目印：◯件」を出し、押すと、まだ確かめていない目印のある入居者だけに絞れる（件数と絞ったあとの行数が一致する）。目印だけの別の画面は作らない。
- **FR-004**: System MUST 目印の文に、医療の判断（病名・病状の評価）や助言を書かない。記録の事実だけを書く。そばに「気になるときは、看護職員・生活相談員に相談してください。急変は電話で」と案内する（Constitution 原則 III）。
- **FR-005**: System MUST 目印が付いても、職員のタブレットに通知・音・画面を遮る表示を出さない（Constitution 原則 II）。
  生活相談員・施設長にも、別の画面や通知で知らせない。全員が同じ入居者一覧（FR-003 の件数）で見る。
- **FR-006**: System MUST 目印を見られる・確かめられるのは、介護職員・リーダー・生活相談員・施設長だけとし、事務員と家族には見せない。
  事務員は職員の画面（入居者一覧・記録の画面）を開けない（spec 001 の contracts。PR #45 ゆう）ので、目印も見えない。入居者一覧の API に事務員だけの分かれ道は作らない。
- **FR-007**: System MUST 家族の画面・通知・問い合わせ AI（spec 004）には、目印を出さない。家族への連絡が要るときは、職員が電話で行う（Constitution 原則 III）。
- **FR-008**: System MUST 決まりに当てはまらなくなったら、目印を消す。付いた・消えた日時と、当てはまった決まり・もとになった記録を、履歴として残す。
  入居者を開いた画面に、その入居者の過去の目印（付いた日・消えた日・当てはまった決まり・確かめた職員・ひとこと）を新しい順に並べる。施設全体の履歴の画面は作らない。

**確かめる（US2）**

- **FR-009**: System MUST 職員が目印に「確かめた」を押し、ひとこと（100 文字まで、任意）を残せる。確かめた職員・日時・ひとことを残す。
- **FR-010**: System MUST 「確かめ済み」の目印は、まだ確かめていない目印と区別して表示する。決まりに当てはまる記録がさらに続いたら、まだ確かめていない状態に戻す。

**決まりを選ぶ（US3）**

- **FR-011**: System MUST 生活相談員と施設長が、管理画面で決まりごとにオン／オフを選べる（施設全体で一括）。変更者・日時・変更内容を残す。
- **FR-012**: System MUST 決まりの条件（何食・何日続けて、など）は、この spec では変えられない（用意したものを使う）。

**安全性・ログ（課題要件より）**

- **FR-013**: System MUST 職員が書いたひとことは、文字としてのみ表示する（タグやスクリプトは実行されない）。
- **FR-014**: System MUST 本番のログに、入居者の氏名・記録の値・ひとことを出さない。目印の番号・決まりの種類・付いた／消えたの別だけを出す。

### Key Entities *(include if feature involves data)*

- **変化の決まり**: 目印を付ける条件（項目・値・何食／何日続けて）、表示名、オン／オフ、変更履歴。
- **変化の目印**: 入居者 × 決まりごとの、当てはまった期間。もとになった記録の一覧、付いた日時、消えた日時、状態（まだ確かめていない／確かめ済み）、確かめた職員・日時・ひとこと。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 決まりに当てはまる記録が保存されてから、職員が入居者一覧を開き直したときに目印が出るまで、1 分以内。
- **SC-002**: 用意した記録の例（当てはまるもの 10 件・当てはまらないもの 10 件。「食事なし」・未記録・取り消しを含む）で、目印の付け間違い・付け忘れが 0 件。
- **SC-003**: 目印の文に、医療の判断や助言が 1 件も含まれない（テストで確認）。
- **SC-004**: 目印が付いても、職員のタブレットに通知・音・画面を遮る表示が 1 件も出ない（テストで確認）。
- **SC-005**: 家族の画面・通知・問い合わせ AI のどこにも、目印が 1 件も出ない（テストで確認）。
- **SC-006**: 職員が、目印の付いた入居者を開いてから、何がいつから当てはまっているかを 10 秒以内に把握できる（デモ時に確認）。

## Assumptions

- この機能の土台は spec 001 の連絡帳の記録（`care_records`）。職員向けの機能なので、非開示の項目も含めて記録を直接読む（spec 001 research.md R-06 の「職員向けは直接読んでよい」）。
- 目印の決まりの条件（2 食・2 日続けて）は、架空のデモに合わせた仮の値。施設や入居者ごとに条件を変える機能は、この spec では作らない。
- 「看護職員」の役割は今のアプリにないので、目印のそばの案内で「看護職員・生活相談員に相談」と書き、相談はアプリの外で行う。
- 入居者一覧の画面は spec 001（ゆうさん担当）。目印の表示はそこに足す。
  - 目印を調べ直す関数（例：`evaluate_change_flags(session, resident_id)`）と、目印・件数を返す関数はみさきが作る。
    ゆうが、記録の保存・修正・取り消しの処理（001-T026）から調べ直す関数を（同じセッションを渡し、関数の中では commit しない）、入居者一覧（001-T028・001-T031）から目印・件数の関数を呼ぶ。
  - 入居者一覧に出すもの（未記録・返事待ち・家族からのメッセージ・承認待ち・目印）の並べ方と置き場所は、ゆうが画面設計を作るときにまとめて決める。
- データは架空の入居者・職員だけを使う。
- 画面の固定の文言は、Constitution の UI 方針（やさしい日本語・ふりがな・多言語）に従う。職員のひとことはふりがなの対象外。
