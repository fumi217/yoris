# Research: spec 006（E：変化の検知）

plan で決めたことと、その理由・ほかに考えた案。spec 001 の [research.md](../001-family-priority-report/research.md)（以下「001 の R-xx」）の決まりは、そのまま使う。
Technical Context に「NEEDS CLARIFICATION」は残っていない（新しいライブラリ・外部サービスを使わないため）。

## R-01 決まりは、記録の値だけで決まる純粋な関数にする

- **決めたこと**：
  - 決まりは `services/change_rules.py` に、**DB に触らない関数**として置く。入力は「1 人の入居者の、決まりに関係する記録の並び」、出力は「当てはまるか・続いた数・当てはまった記録の id と値」。
  - 決まりは次の 3 つ（spec の FR-002）。コードで持ち、条件（何食・何日）は変えられない（FR-012）。

    | コード | 対象の記録（`care_records`） | 当てはまる値 | 何回続けて |
    |---|---|---|---|
    | `meal_low` | `item = meal`、`slot` が `breakfast`・`lunch`・`dinner`（`snack` は数えない） | `2`（少し）・`0`（食べていない） | 2 食 |
    | `mood_low` | `item = mood`、`slot = day` | `low`（元気がない） | 2 日 |
    | `sleep_poor` | `item = sleep`、`slot = day` | `poor`（あまり眠れなかった） | 2 日 |

  - AI は使わない。様子のメモ（spec 007）などの文は読まない（spec の Clarifications）。
- **理由**：同じ記録からはいつも同じ結果になり、目印が付いた理由を記録の事実だけで説明できる（原則 III）。DB なしで動くので、SC-002 の 20 件をそのまま単体テストにでき、作る順番の最初に置ける。
- **ほかに考えた案**：SQL のウィンドウ関数で判断する（「すきま」の扱いが SQL では読みにくく、テストに DB が要る）、AI に記録を読ませて判断する（spec で採らないと決めた）。

## R-02 「続けて」の数え方（未記録・食事なし・取り消し）

- **決めたこと**：
  - 決まりごとに、時間の順の「枠」を並べる。食事は日ごとに 朝ごはん → 昼ごはん → 夜ごはん の 3 枠、機嫌・眠りは 1 日 1 枠。日付は日本時間の連絡帳の日付（001 の R-14。眠りは記録した朝の日付、001 の R-05）。
  - **いちばん新しい記録のある枠から、さかのぼって数える**。まだ記録がない「これからの枠」（例：お昼の時点での夜ごはん）は数えない。
    - 当てはまる値 → 続いた数を 1 増やす
    - 記録がない枠（未記録）・取り消した記録の枠・「食事なし（`none`）」の枠 → **すきま**。当てはまる値としては数えない
    - すきまが 2 枠続いた（食事は 2 食、機嫌・眠りは 2 日） → そこで数えるのをやめる（spec の「食事は 1 食、機嫌・眠りは 1 日までの未記録なら飛ばす。それより長くあいたら数え直す」）
    - 当てはまらない値（例：「ほぼ全部」「いつもどおり」） → そこで数えるのをやめる
  - 続いた数が 2 以上なら「当てはまる」。当てはまった記録（すきまは含まない）の id・日付・枠・値を返す。
  - さかのぼるのは直近 7 日まで（1 回に読む記録を少なくするため。7 日より長く続いても、目印は付いたまま）。
- **「食事なし」を「すきま」にする理由**：spec は「食事なしは食べていないとして数えない」「入院で何日も食事なしが続いても目印は付けない」と決めている。
  すきまとして扱えば、どちらも満たし（食事なしが 2 食続けば数え直しになる）、外泊から戻った 1 食の前後の「少し」を、未記録と同じように続けて数えられる。
  **plan での仮の判断**なので、この PR のレビューで確かめる（plan の「未決定のこと」）。
- **例**（spec の Edge Cases と同じ）：
  - 機嫌：月「元気がない」・火 未記録・水「元気がない」 → 続いた数 2（火はすきま 1 日）→ 当てはまる
  - 機嫌：月「元気がない」・火〜木 未記録・金「元気がない」 → 火・水ですきまが 2 日続くので数えるのをやめる → 続いた数 1 → 当てはまらない
  - 食事：昼「少し」・おやつ「食べていない」 → おやつは枠に入らない → 続いた数 1 → 当てはまらない（次の夜ごはんで決まる。spec の US1 シナリオ 3a）
  - 食事：前の日の夜「少し」・朝「食べていない」 → 続いた数 2 → 当てはまる（spec の US1 シナリオ 1）
- **ほかに考えた案**：「食事なし」で数え直す（外泊の前後の変化を見落とす）、未記録も当てはまらない値として数え直す（spec の「短いあいだは飛ばす」に合わない）。

## R-03 記録の保存と同じトランザクションで、作り直して突き合わせる

- **決めたこと**：
  - `services/change_detection.py` に `evaluate_change_flags(session, resident_id)` を置く。ゆうの記録の保存・押し直し（`services/records.py`、001-T026）と取り消し（001-T034）が、処理のあとに**同じセッションを渡して**呼ぶ。
    **関数の中では commit しない**（spec 001 の `create_reply_notice` と同じ形。001 の R-09、PR #40 ゆう）。
  - 中身は「作り直して突き合わせる」形にする。
    1. オンの決まりごとに、その入居者の、取り消していない記録のうち、いちばん新しい記録の日を含む 7 日分（その日から 6 日前まで。今日ではなく、その入居者の最新の記録の日で数える）を読み、R-01 の関数で今の状態を出す
    2. 今の目印（`change_flags` の `cleared_at` が空のもの）と突き合わせる
       - 当てはまる・目印がない → 目印を作る（まだ確かめていない）
       - 当てはまる・目印がある → もとの記録と続いた数を上書きする。確かめ済みで、続いた数が確かめたときより増えた → まだ確かめていないに戻す（FR-010）
       - 当てはまらない・目印がある → 目印を消す（`status = cleared` と `cleared_at`・`cleared_reason` をまとめて入れる。履歴として残る。FR-008）
  - 同じ入居者の調べ直しが同時に走らないよう、最初に **`residents` テーブルのその入居者の行**を `SELECT ... FOR NO KEY UPDATE`（SQLAlchemy では `with_for_update(key_share=True)`）で押さえる（記録の保存は同じ入居者に 2 人が同時に行うことがあるため）。**`FOR UPDATE` にはしない**：記録を新しく足すと、外部キーの確認で入居者の行に `FOR KEY SHARE` が付き、`FOR UPDATE` だと、2 人が同時に新しく記録したとき、お互いの `KEY SHARE` の終わりを待ち合って止まる（`deadlock detected`。PR #310 のゆうの指摘）。`FOR NO KEY UPDATE` は `KEY SHARE` と両立し、`FOR NO KEY UPDATE` どうしは待つので、調べ直しを順番にする目的は変わらない。`change_flags` の行ではなく入居者の行を押さえるのは、目印がまだない入居者でも同時の調べ直しが順番に処理され、一意制約の違反にならないようにするため（PR #45 の AI チューター・ゆうの指摘）。確かめる処理（R-04）も同じ順番（入居者の行 → 目印の行）で押さえ、互いに待ち合って止まらないようにする。
  - 初期データ（`seed`）で記録を入れたあとも、全員について呼ぶ。
- **理由**：記録だけ保存されて目印がずれる、ということが起きない。何度呼んでも同じ結果になる（同じ記録なら同じ目印）ので、押し直し・取り消し・保存のやり直しのどれでも正しくそろう。
  1 人分・7 日分なので、記録の保存の応答をほとんど遅くしない。
- **ほかに考えた案**：worker で決まった時刻に全員を調べる（SC-001 の 1 分以内に間に合わせるには短い間隔で回す必要があり、本番の Render の無料プランでは worker を常に動かせない。#28・#34）、
  画面を開いたときに毎回その場で計算して保存しない（「付いた日・消えた日」と「確かめた」を残せない）、差分だけを足し引きする（取り消し・押し直しで食い違いやすい）。

## R-04 目印のまとめ方と「確かめた」

- **決めたこと**：
  - データは**入居者 × 決まり**ごとに 1 行（`change_flags`）。画面では入居者ごとにまとめ、決まりが 2 つ当てはまっていても目印は 1 つ（spec の Edge Cases）。
  - 「確かめた」は**入居者ごとに 1 回**押す。押すと、その入居者の今の目印のうち、まだ確かめていないものがまとめて確かめ済みになる。確かめた職員・日時・ひとこと（100 文字・任意）・そのときの続いた数を `change_flag_confirmations` に残す。
    確かめ直したら行が増え、前に確かめた人の記録も残る（次の勤務の人が見返せる。spec の US2）。
  - 「確かめていない目印：◯件」は、**まだ確かめていない目印がある入居者の人数**で数える（spec の US2 シナリオ 1a「3 人 → 3 件」）。
  - 2 人がほぼ同時に「確かめた」を押したら、先に保存されたほうだけを残し、後の人には「ほかの職員が確かめました」と表示する（409）。
- **理由**：画面と spec の数え方（入居者ごと）に合わせると、職員は「この人を確かめた」を 1 回押せば済む（原則 II）。決まりごとに行を分けると、「何が当てはまり、いつ消えたか」を決まりごとに履歴に残せる。
  **数え方と確かめる単位は plan での仮の判断**なので、この PR のレビューで確かめる。
- **ほかに考えた案**：決まりごとに「確かめた」を押す（当てはまった決まりが 2 つだと 2 回押すことになる）、入居者ごとに 1 行にまとめる（決まりごとの「消えた日」を残せない）。

## R-05 見せる相手を職員（事務員を除く）に限る

- **決めたこと**：
  - 目印の API（入居者の目印・確かめた・決まりの設定）は、`require_staff(roles)` で役割を確かめる。目印を見る・確かめる：介護職員・リーダー・生活相談員・施設長。決まりのオン／オフ：生活相談員・施設長（FR-006・FR-011）。
    ほかの役割と家族は 403（`forbidden`。spec 001 の「役割がない」の決まり）。画面は、家族なら「ページが見つかりません」。事務員は職員の画面そのものを開けない。
  - 入居者一覧の API（ゆう）は、spec 001 のとおり介護職員・リーダー・生活相談員・施設長だけが開ける（事務員は 403）。そのため、目印も見えない。一覧の API は事務員で分けず、いつも `get_flag_summary` の結果を足す（PR #45 ゆう。#40 の「事務員も開く」を直した）。
  - 目印のテーブルは、spec 001 の共通の関数（`get_disclosed_records`・`get_disclosed_themes`・`get_active_replies`）からも、家族の API・通知のまとめ・問い合わせ AI（spec 004）のツールからも読まない（FR-007）。
    テストで、家族の連絡帳・通知のまとめ・AI のツールの返す値に目印が入らないことを確かめる（SC-005）。
- **理由**：体調に関わる情報を、お世話に関わる職員だけに見せる（spec の Clarifications）。家族に出す道を通らない別のテーブルにしておけば、家族に漏れる道がそもそもない。

## R-06 目印の文は、コードで返して辞書から引く

- **決めたこと**：
  - API は文言を返さず、**決まりのコード**（`meal_low` など）と、**もとの記録のコード**（日付・`slot`・`value`）、続いた数だけを返す（spec 001 の「文言はコードで返す」）。
  - 画面は辞書から文言を組み立てる（例：「食事量：昨日の夜ごはんから 2 食続けて、少し以下」）。目印の名前「⚠️ いつもと違う様子」と、そばの案内「気になるときは、看護職員・生活相談員に相談してください。急変は電話で」も辞書に置く（FR-004）。
  - 辞書の目印まわりの文に、医療の言葉（病気・疑い・診断・症状・脱水 など）が入っていないことを、Vitest で確かめる（SC-003）。
- **理由**：サーバーから自由な文を返さないので、医療の判断が入る道がない。ふりがな・多言語も、ほかの画面と同じ仕組みで付けられる（001 の R-11）。

## R-07 決まりのオン／オフ

- **決めたこと**：
  - 決まりは `change_rules` に 3 行（初期値はすべてオン）。生活相談員・施設長が管理画面で施設全体のオン／オフを変え、変更者・日時・前後の値を `change_rule_histories` に残す（FR-011）。
  - **オフにしたら、その決まりの今の目印を消す**（消えた理由を「決まりをオフにした」として残す）。オフのあいだは調べない。
  - **オンに戻したら、入居者全員について `evaluate_change_flags` を呼ぶ**（30 人分。オン／オフの保存と同じトランザクション）。
- **理由**：オフにしたのに目印が残ると、職員が「なぜ残っているのか」と迷う。オンに戻したときに全員を調べ直せば、オフのあいだに入った記録も反映される。
  **オフにしたときに今の目印を消すかは plan での仮の判断**なので、この PR のレビューで確かめる。

## R-08 ログとテスト

- **ログ**（001 の R-18）：目印の id・決まりのコード・付いた／消えた／確かめたの別・入居者の id だけを出す。入居者の氏名・記録の値・ひとことは出さない（FR-014）。
- **テスト**（001 の R-19）：
  - 単体（DB なし）：決まりの関数に、当てはまる 10 件・当てはまらない 10 件の記録の並びを渡し、付け間違い・付け忘れが 0 件（SC-002）。「食事なし」・未記録・取り消し・おやつ・7 日を超える並びを含める
  - API（テスト用の PostgreSQL）：保存・押し直し・取り消しで目印が付く・消える、続いたら確かめ済みから戻る、決まりのオン／オフ、役割ごとに 403 になる（事務員・家族）、事務員が入居者一覧を開くと 403、
    家族の連絡帳・通知のまとめ・AI のツールに目印が入らない（SC-005）、目印が付いても通知（`notifications`・`email_outbox`）が増えない（SC-004）
  - Vitest：目印の文の組み立て、辞書に医療の言葉が入っていない（SC-003）、絞り込み
