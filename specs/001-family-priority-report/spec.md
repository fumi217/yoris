# Feature Specification: 家族ごとに「知りたい順」で届く日報（スプリント1: C→B→A）

**Feature Branch**: `001-family-priority-report`

**Created**: 2026-10-19

**Status**: Draft

**Input**: User description: "スプリント1（C→B→A）: 職員が食事量を5段階ボタンで記録（献立から食材表示）→ 施設が家族に開示する記録項目を選ぶ → 家族が「知りたいこと」をボタンで優先度つきで選び、職員の記録から家族ごとに内容・並び順が変わる日報を、アプリを開いたら一番知りたいことが一番上に出る形で見られる。未確定事項（プッシュ通知の内容・頻度と緊急時の電話/SMSをAに含めるか、紙の日報をやめタブレット直接入力前提でよいか）を spec 内で確認する。"

## 背景と解決する困りごと

| ペルソナ | 困りごと | この機能で変わること |
|---|---|---|
| 佐藤美紀（家族） | 昼休みしか電話できず、遠慮して聞けない。月 1 回の報告では知りたいことが分からない | アプリを開くと、自分が一番知りたいこと（例: 母がごはんを食べたか）が一番上に出ている |
| 田中健太（介護職員） | IT が苦手。ケア中に家族の電話で呼ばれる | ボタンを押すだけで記録でき、家族への説明はその記録から自動で届く |
| シティさん（介護職員） | 日本語の記録に時間がかかる | 食事量は文字を書かずにボタンで記録できる（多言語表示） |
| 山本由美（生活相談員） | 家族対応の窓口として問い合わせが集中する | 家族に何を見せるかを項目単位で設定でき、よくある質問が減る |

## User Scenarios & Testing *(mandatory)*

> 優先度はスプリント 1 の組み立て順（C → B → A）に合わせている。スプリントの**目的**は
> ユーザーストーリー 3（家族が知りたい順に見る）であり、成功基準もそこに置く。
> 各ストーリーは、前のストーリーのデータを架空の初期データで置き換えれば単独でデモできる。

### User Story 1 - 職員が食事量をボタンで記録する（C） (Priority: P1)

介護職員（田中さん・シティさん）は、食事が終わったらタブレットで入居者を選び、
その食事の献立（料理名と主な食材）を見ながら、食べた量を 5 段階のボタンで記録する。
文字を入力する必要はない。

**Why this priority**: 家族向け日報の元になる記録がなければ、開示も家族ごとの並べ替えも
成立しない。食事は家族が最も気にする情報の一つで、ボタン化による入力負担の削減も示せる。

**Independent Test**: 献立を登録した状態で、職員が 30 人分の昼食の食事量を記録し、
記録一覧に入居者ごと・食事ごとの食事量と記録者・時刻が残ることを確認する。

**Acceptance Scenarios**:

1. **Given** 今日の昼食の献立が登録されている, **When** 職員が入居者「佐藤さんの母」を選んで昼食を開く,
   **Then** 料理名と主な食材が絵文字つきで表示され、食事量の 5 段階ボタンが表示される
2. **Given** 昼食の記録画面を開いている, **When** 職員が「ほぼ ぜんぶ（8わり）」ボタンを押す,
   **Then** 文字入力なしで記録が保存され、記録者と時刻が残る
3. **Given** 記録済みの食事がある, **When** 職員が別の段階を押し直す,
   **Then** 記録が上書きされ、修正したことが履歴として残る
4. **Given** 表示言語をインドネシア語に切り替えた職員, **When** 記録画面を開く,
   **Then** 5 段階ボタンと食事区分のラベルがインドネシア語（絵文字つき）で表示される
5. **Given** 献立が登録されていない食事, **When** 職員が記録画面を開く,
   **Then** 「こんだて みとうろく」と表示され、食事量の記録はそのまま行える

### User Story 2 - 施設が家族に見せる記録項目を選ぶ（B） (Priority: P2)

生活相談員（山本さん）または施設長は、介護記録のうちどの項目を家族に見せるかを
項目ごとにオン／オフで設定する。オフにした項目は、家族側のどこにも出ない。

**Why this priority**: 施設が安心して導入できる条件であり（Constitution 原則 IV）、
家族が「知りたいこと」として選べる範囲もこの設定で決まる。

**Independent Test**: 「食事量」をオン、「体重」をオフにした状態で家族アカウントでログインし、
食事量は見えて体重はどの画面にも出ないことを確認する。

**Acceptance Scenarios**:

1. **Given** 施設の管理画面, **When** 相談員が記録項目の一覧を開く,
   **Then** 各項目に「家族に見せる／見せない」の切り替えが表示される
2. **Given** 「食事量」を見せない設定にした, **When** 家族が日報を開く,
   **Then** 食事量はどこにも表示されず、知りたいことの選択肢からも消える
3. **Given** 家族が「食事」を知りたいことの 1 位にしていた, **When** 施設が食事量を非開示にする,
   **Then** 家族の画面では次に優先度が高い開示項目が一番上に繰り上がり、
   「しせつの せっていで ひょうじ されない こうもくが あります」と案内される
4. **Given** 開示設定を変更した, **When** 施設長が変更履歴を見る,
   **Then** いつ・誰が・どの項目を変えたかが分かる

### User Story 3 - 家族が「知りたいこと」を選び、知りたい順の日報を見る（A） (Priority: P3)

家族（佐藤さん）は初回に、知りたいことを絵文字つきのボタンから選び、順番を付ける
（例: 1 位 🍚ごはん、2 位 😊きげん・ようす、3 位 😴ねむり）。
以降アプリを開くと、今日の日報が自分の順番で並び、1 位の項目がいちばん上に大きく出ている。
同じ入居者の別の家族（例: 佐藤さんの兄）は、自分の順番で同じ記録を違う並びで見る。

**Why this priority**: スプリント 1 のゴールそのもの（Constitution 原則 I）。
P1・P2 がそろうことで、実際の職員記録から家族ごとの日報が出る。

**Independent Test**: 架空の記録（食事・きげん・ねむりなど）を用意し、優先順位の異なる
2 つの家族アカウントで開いたとき、それぞれの 1 位がファーストビューの一番上に出ることを確認する。

**Acceptance Scenarios**:

1. **Given** 初めてログインした家族, **When** 「しりたいこと」の選択画面を開く,
   **Then** 施設が開示している項目だけが絵文字つきボタンで表示され、3 つ以上を選んで順番を付けられる
2. **Given** 1 位を「🍚ごはん」にした家族, **When** アプリを開く,
   **Then** ファーストビューの一番上に今日の食事（どの食事を、どれくらい食べたか、献立）が表示される
3. **Given** 同じ入居者に家族 A（1 位: ごはん）と家族 B（1 位: ねむり）がいる, **When** それぞれが日報を開く,
   **Then** 同じ日の同じ記録が、A は食事、B は睡眠を一番上にして表示される
4. **Given** 今日まだ夕食が記録されていない, **When** 家族が日報を開く,
   **Then** 夕食は「まだ きろく されていません」と表示され、推測で埋められない
5. **Given** 家族が優先順位を変えたい, **When** 設定から順番を入れ替える,
   **Then** 次に日報を開いたときから新しい順番で表示される
6. **Given** 職員が昼食を記録した, **When** 家族が日報を開き直す,
   **Then** 記録から 5 分以内にその内容が日報に反映されている
7. **Given** 過去の日付, **When** 家族が日付を戻す,
   **Then** 過去 30 日分の日報を同じ優先順で見られる

---

### Edge Cases

- 家族が知りたいことを 1 つも選ばずに閉じた場合 → 施設の既定の並び順（食事 → きげん・ようす → …）で表示し、
  上部に「しりたいことを えらぶと、いちばん うえに でます」と案内する。
- 1 人の入居者に複数の家族アカウントがある場合 → 優先順位は家族アカウントごとに独立して保存する。
- 家族が別の入居者の日報を見ようとした場合（URL 改変など） → 表示せず、アクセスを拒否する。
- 入居者が外泊・入院などで食事が提供されなかった場合 → 職員は「たべていない」ではなく
  「しょくじ なし（がいはく など）」を選べ、家族には区別して表示される。
- 職員が誤って別の入居者に記録した場合 → 職員は当日中に取り消せ、家族の日報からも消える。
- 施設がすべての項目を非開示にした場合 → 家族には「いま みられる きろくは ありません」と表示する。
- 食事量が 2 食続けて「ほとんど たべていない」以下だった場合 → スプリント 1 では家族への特別な通知は行わない
  （変化の検知・通知は E としてスプリント 3 で扱う）。

## Requirements *(mandatory)*

### Functional Requirements

**C. 食事量の記録（職員）**

- **FR-001**: System MUST 食事区分（あさ・ひる・ゆう・おやつ）ごとに、入居者の食事量を 5 段階のボタンで記録できる。
  5 段階は「ぜんぶ（10わり）／ほぼぜんぶ（8わり）／はんぶん（5わり）／すこし（2わり）／たべていない（0）」とする。
- **FR-002**: System MUST 5 段階とは別に「しょくじ なし（がいはく・にゅういん など）」を選べる。
- **FR-003**: System MUST 記録画面に、その食事の献立（料理名・主な食材）を絵文字つきで表示する。
- **FR-004**: System MUST 施設が日付・食事区分ごとに献立（料理名と主な食材）を登録できる。
- **FR-005**: System MUST 記録ごとに記録者・記録時刻・修正履歴を保持する。
- **FR-006**: System MUST 食事量の記録を文字入力なしで完了できる（入居者選択から保存まで 3 タップ以内）。
- **FR-007**: System MUST 職員画面のボタン・ラベルを日本語とインドネシア語・英語で切り替えて表示できる。
- **FR-008**: System MUST 未記録の入居者が分かるよう、食事区分ごとに記録済み／未記録の一覧を職員に表示する。

**B. 開示項目の設定（施設）**

- **FR-009**: System MUST 施設（生活相談員・施設長の役割）が、記録項目ごとに家族への開示／非開示を設定できる。
- **FR-010**: System MUST 非開示の項目を、家族向けの日報・知りたいことの選択肢・その他の家族向け表示のいずれにも出さない。
- **FR-011**: System MUST 開示設定の変更を、変更者・日時・変更内容とともに記録する。
- **FR-012**: System MUST 開示設定の変更を、次に家族が日報を開いたときに反映する。

**A. 家族ごとの優先度つき日報（家族）**

- **FR-013**: Families MUST be able to 開示されている項目の中から、知りたいことを絵文字つきボタンで選び、順位を付けられる。
- **FR-014**: System MUST 家族アカウントごとに優先順位を保存し、同じ入居者の他の家族の設定に影響させない。
- **FR-015**: System MUST 家族が日報を開いたとき、優先順位 1 位の項目をファーストビューの一番上に、
  以降を優先順に並べて表示する。
- **FR-016**: System MUST 日報の内容を職員の記録から自動で作り、家族向けのための追加入力を職員に求めない。
- **FR-017**: System MUST 未記録の項目は「まだ きろく されていません」と表示し、推測や空欄で表示しない。
- **FR-018**: System MUST 職員の記録を 5 分以内に家族の日報へ反映する。
- **FR-019**: System MUST 家族が過去 30 日分の日報を日付を選んで見られる。
- **FR-020**: System MUST 家族アカウントに、紐づいた入居者以外の情報を表示しない。
- **FR-021**: System MUST 家族向け画面で、漢字にかなを多めに使い、各項目に絵文字を付けて表示する。

**スプリント 1 で記録する項目の範囲**

- **FR-022**: System MUST スプリント 1 で家族の日報に出せる記録項目として、食事量に加えて
  [NEEDS CLARIFICATION: 食事以外の項目（きげん・ようす、ねむり、おふろ、たいちょう など）をスプリント 1 でボタン記録まで作るか？ 作らない場合、家族が「知りたいこと」を選んでも実データは食事だけになり、並べ替えのデモ効果が弱い]

**通知と緊急連絡**

- **FR-023**: System MUST [NEEDS CLARIFICATION: プッシュ通知（「きょうの にっぽうが とどきました」等）の内容・頻度の設定と、緊急時は電話や SMS で連絡するという運用・表示を A（スプリント 1）に含めるか？]

**記録媒体**

- **FR-024**: System MUST [NEEDS CLARIFICATION: 紙の日報をやめてタブレットで直接入力する前提でよいか？ 紙と併用する場合、家族の日報に出るのはタブレットに入力された分だけになる]

**安全性・ログ（課題要件より）**

- **FR-025**: System MUST 献立の料理名・食材など施設や職員が入力した文字を、家族・職員の画面で
  文字としてのみ表示する（入力に含まれるタグやスクリプトは実行されない）。
- **FR-026**: System MUST 入力値を、記録の検索・保存の命令の一部として解釈させない
  （SQL インジェクションを含む不正な入力を受けても、ほかの入居者の記録が読み書きされない）。
- **FR-027**: System MUST 開発環境と本番環境でログの詳しさを分け、本番のログには
  入居者・家族の氏名や記録内容を出さない。

### Key Entities *(include if feature involves data)*

- **入居者**: 施設に入居している人。氏名、居室、表示用の呼び名。1 人に複数の家族が紐づく。
- **家族アカウント**: 入居者に紐づく家族。続柄、表示言語。1 アカウントは原則 1 人の入居者に紐づく。
- **職員**: 介護職員・リーダー・生活相談員・事務員・施設長などの役割と、表示言語を持つ。
- **献立**: 日付 × 食事区分ごとの料理名と主な食材（絵文字つき）。
- **食事記録**: 入居者 × 日付 × 食事区分ごとの食事量（5 段階 or しょくじなし）、記録者、時刻、修正履歴。
- **記録項目**: 食事量など、家族に見せうる記録の種類。表示名・絵文字・既定の並び順を持つ。
- **開示設定**: 施設 × 記録項目ごとの開示／非開示と、その変更履歴。
- **知りたいこと（優先設定）**: 家族アカウント × 記録項目ごとの順位。
- **日報**: 入居者 × 日付の記録を、閲覧する家族の優先設定と施設の開示設定で並べ替え・絞り込みして見せるもの
  （保存される文書ではなく、記録から都度組み立てる表示）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 家族がアプリを開いてから、自分が 1 位に選んだ情報を読み終えるまでに、スクロールなしで 10 秒以内である。
- **SC-002**: 優先順位の異なる 2 つの家族アカウントで同じ日の日報を開くと、100% の確率でそれぞれの 1 位が一番上に表示される。
- **SC-003**: 職員 1 人が 1 食分の食事量を、入居者選択から保存まで 10 秒以内・3 タップ以内で記録できる。
- **SC-004**: 職員が 30 人分の昼食の食事量を 5 分以内に記録し終えられる。
- **SC-005**: IT が苦手な職員（田中さん想定）が、説明 5 分以内で迷わず初回の記録を完了できる（デモ時に確認）。
- **SC-006**: 非開示にした項目が、家族向けのどの画面にも 1 件も表示されない（全画面を確認するテストで 0 件）。
- **SC-007**: 家族が初回に「知りたいこと」を選び終えるまで 1 分以内である。
- **SC-008**: 職員の記録から家族の日報への反映が 5 分以内である。
- **SC-009**: 献立名に `<script>` などを含む文字列を登録しても、家族・職員のどの画面でも実行されず文字として表示される（テストシナリオで確認）。

## Assumptions

- 献立は施設が事前に登録する。スプリント 1 のデモでは 1 週間分の架空献立を初期データとして用意し、
  献立登録画面は最小限（料理名・食材・絵文字の入力）とする。
- 食事量は 1 食につき 1 つの 5 段階で記録する（品目ごとの記録は職員の負担が増えるため行わない）。
- 家族アカウントの発行は施設（生活相談員）が行い、家族は招待を受けて登録する。
  認証は一般的なメールアドレスとパスワード方式を想定する。
- 家族は主にスマートフォン、職員は施設のタブレットで利用する。
- データは架空の入居者・家族・職員のみを使う（Constitution 共通の設計制約）。
- AI による文章の生成・翻訳（D）、変化の検知・通知（E）、問い合わせ AI（F）、面会予約（G）、
  アルバム（H）、システム利用料（J）はスプリント 1 の範囲外とする。
  立替金の精算は Constitution により対象外。
- 規模は施設 1 つ、入居者最大 30 人、職員 16 人、家族アカウントは入居者 1 人あたり最大 3 人を想定する。
- 過去の日報の保持期間は 30 日分を家族に表示する（記録自体の保存期間は介護記録の法定保存に従い、別途定める）。
