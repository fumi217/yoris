## R-01 職員のログインの仕方

- **決めたこと**：
  - 職員は**一人ずつ ID（`login_id`）を付与して**ログインする。家族はメールアドレスでログインする（開発前MTG で決まったこと）。
    ログインの情報は、職員と家族で共通の `users` テーブルに置く（形はようこが決めて共有する）。
  - 職員のアカウントは、管理画面で作って初期パスワードを渡す。招待（`invitations`）は家族だけにする。
  - タブレットを共有するため、**職員は操作がないまま 30 分たったら自動でログアウト**する。家族は 30 日。ログアウトしたらセッションをすぐ消す。
- **理由**：介護職員は仕事用のメールアドレスを持っていないことが多い。記録者・返事をした職員の表示名を確実に残すため（FR-005・FR-030）、交代のときのログアウト忘れで前の人の名前が残らないようにする（PR #17 ようこ）。
- **ほかに考えた案**：
  - 職員もメールアドレスでログインする：メールアドレスを持っていない職員が使えない。
  - 共有のタブレットに施設としてログインし、記録するたびに名前を選ぶ：ほかの人の名前を選べてしまい、記録者が正しく残る保証がない。
  - 職員のログインを 12 時間続ける：ログアウトを忘れると、次の人の記録が前の人の名前で残る。

## R-02 開発用のユーザー切り替え

- **決めたこと**：開発環境（`APP_ENV=development`）だけで動く `POST /api/dev/switch-user` を作り、初期データの職員・家族を選ぶとその人としてログインした状態にする。
  本番ではルーター自体を登録しない。**`APP_ENV` が設定されていないときは production として扱う**（開発用でない側に倒す）。
  本番の設定で `/api/dev/switch-user` が 404 になることを、テストで確かめる（R-19）。
- **理由**：Day 1〜3 のミニマム版で「職員として記録 → 家族に切り替えて確認」をすぐできる。本番で動かないことを、設定の付け忘れも含めて確実にする（開発前MTG・PR #17 ようこ）。
- **ほかに考えた案**：毎回ログイン画面から入り直す（デモが遅くなる）、ヘッダーで人を指定する（本番に残ったときの危険が大きい）。

## R-03 ログインとセッション

- **決めたこと**：
  - バックエンドが発行するセッション（Cookie、Redis に保存）。Cookie は `HttpOnly`・`Secure`（本番）・`SameSite=Lax`。
    書き込みの API は、`SameSite=Lax` に加えて、フロントが付ける独自のヘッダー（`X-Requested-With: fetch`）があることを確かめる（CSRF 対策）。
  - **フロントとバックエンドを同じオリジンにする**：ブラウザからは `/api` をフロントと同じオリジンで呼び、バックエンドへ中継する（開発は Vite の proxy、本番はフロントの配信側の中継）。
    同じオリジンなので CORS の設定はいらない（許可するオリジンを開けない）。
  - **本番の構成**：フロントは Render の **Static Site**（ビルドした静的ファイルを置くだけ）、バックエンドは Render の無料の **Web Service** 1 つ。
    Static Site の書き換えのルール（rewrite）で、`/api/*` をバックエンドの公開 URL（`https://<バックエンド>/api/*`）に中継する。書き換え先は公開 URL でなければならない（Render の内部の URL は使えない）。
    無料の Web Service は、アカウント全体で月 750 時間まで使える。R-09 の外部のスケジューラーが 1 分ごとに呼ぶとバックエンドは起きたままになり、それだけで約 744 時間を使うので、**ほかに無料の Web Service を置かない**。Static Site はこの時間を使わない（PR #34 ゆう・さとこ）。
    中継を通しても、ログインの Cookie（`Set-Cookie`）がフロントのオリジンで受け取れ、次のリクエストに付くことは、本番デプロイ（T092）の最初に確かめる。
  - パスワードは bcrypt で保存する。**パスワードの決まり**（職員・家族・施設長のすべてのログインで共通。spec 002 の申し込みページも同じ）：
    - **8 文字以上、64 文字まで**。文字の種類の組み合わせ（大文字・数字・記号を必ず入れる、など）は求めない。求めると `Password1!` のような決まった形が増え、かえって破られやすいため
    - **よく使われるパスワード・漏れたパスワードの一覧と照らし合わせ、当てはまれば使わせない**。一覧はファイルでアプリに置く（外のサービスに問い合わせない）
    - **使える文字は、半角の英数字と記号（キーボードで打てる文字。空白も含む）だけ**。かな・漢字・全角の文字は使えない（422）。
      日本語の入力がオンのまま打つと、見た目が同じでも全角の `Ａ` と半角の `A` のように違う文字になり、
      濁点の付いた文字は端末によって表し方が違うので、同じパスワードのつもりでもログインできないことがあるため。
      インドネシア語・英語の職員も打ちやすい。半角だけなら 64 文字で 64 バイトなので、bcrypt の 72 バイトの上限も超えない（#65 で決定。もとは全角も使えて、72 バイトを超えたら 422 だった）
    - 長さの理由：NIST SP 800-63B 第 4 版（2025-08）では、パスワードだけでログインする場合は 15 文字以上が基準（8 文字以上は二段階認証と組み合わせる場合）。
      職員が共有タブレットで、操作がないまま 30 分で自動ログアウトするたびに打つ負担（Constitution 原則 II）を考え、8 文字以上にする。
      代わりに、よく使われるパスワードを弾くことと、ログインの試行回数の制限（下）で補う（PR #25 でチームが決定）
  - 作り込みの余力があれば、**家族のログインにパスキー**を足す（パスワードの代わりではなく追加。家族は自分のスマートフォンで使うので、パスキーの良さが活きる。
    職員は共有タブレットなので向かない。本番のドメインが決まってから設定する。spec 002 の clarify で決定）。
  - 家族の招待は、1 回だけ使えるトークン（7 日で切れる）をメールで送る。トークンは URL のパスに入れず、メールのリンクは `#token=` の形にして、
    画面がトークンをリクエストの本文で送る（サーバーのアクセスログにトークンが残らない）。
  - ログインの試行回数を Redis で制限する（例：同じ ID で 15 分に 10 回まで）。
- **理由**：技術選定の `app.`・`api.` の別サブドメインのままだと、Render の `*.onrender.com` が Public Suffix List に入っているため別のサイトとして扱われ、
  `SameSite=Lax` の Cookie が fetch に付かず、本番でログインできなくなる（PR #17 ようこ）。同じオリジンにすれば、独自ドメインを取る前でも動く。
- **ほかに考えた案**：Day 1 から独自ドメインにして `app.`・`api.` を同じサイトにする（ドメインの準備が先に要る）、`SameSite=None` にする（CSRF の守りが弱くなる）、JWT（取り消しがしにくい）、外部の認証サービス（設定を覚える時間がかかる）。
- **未決定**：家族がパスワードを忘れたとき。案は「ミニマム版では施設がもう一度招待する、再設定の画面は作り込みで検討」（[plan.md 未決定のこと](./plan.md#未決定のこと)）。

## R-04 記録のテーブルを 1 つにまとめる

- **決めたこと**：食事量・機嫌・眠りを 1 つのテーブル `care_records` にまとめ、`item`（meal／mood／sleep）と `slot` で区別する（開発前MTG）。
  `slot` は、食事は `breakfast`／`lunch`／`dinner`／`snack`、機嫌・眠りは `day` とし、空にしない。
  「入居者×日付×項目×区分は 1 つだけ」は、**取り消していない記録だけ**を対象にした一意制約（部分インデックス、`WHERE deleted_at IS NULL`）にする。
- **理由**：開示設定が項目ごとなので `item` で絞るだけで済み、連絡帳・AI・E が同じテーブルを読める。
  PostgreSQL の一意制約では空どうしが別物として扱われ、同じ日の機嫌が 2 つ入ってしまうため `slot` を空にしない。取り消したあとに記録し直せるよう、一意制約は取り消していないものだけにする。
- **ほかに考えた案**：項目ごとにテーブルを分ける（読む側が 3 つを組み合わせる必要があり、開示の絞り込みも 3 か所になる）。

## R-05 眠りの日付

- **決めたこと**：眠りは「前日の夜に眠れたか」を、**記録した朝の日付**の記録にする。画面には「昨夜の眠り」と書く（開発前MTG で決まったこと）。
- **理由**：職員は朝に前の夜の様子を記録するので、記録した日と連絡帳の日がそろう。E（変化の検知）で「続けて」を数えるときも、日付が 1 本の並びになる。
- **ほかに考えた案**：眠った夜の日付で持つ（記録した日と連絡帳の日がずれて、未記録の一覧が分かりにくい）。

## R-06 家族に出すときの共通の関数

- **決めたこと**：`backend/app/services/disclosure.py` に次の共通の関数を置く（作る人はゆう。開発前MTG。`is_item_disclosed` は PR #44 で追加）。
  - `get_disclosed_records(session, resident_id, date_from, date_to, items=None)`：開示済みの、取り消していない記録。id・日付・項目・区分・値・記録した時刻・記録した職員の表示名を返す。`items` で項目を絞れる
  - `get_disclosed_themes(session)`：開示済みの「知りたいこと」のテーマ
  - `get_requested_themes(session, theme_ids)`：家族がすでに送ったリクエストのテーマ。開示の設定に関わらず返す（送ったあとにテーマが非開示になっても、送ったリクエストは残るため。テーマ名を出すときも、直接 JOIN せずにここを通す。issue #111 さとこ）
  - `is_item_disclosed(session, code)`：その記録項目を家族に見せる設定か。spec 007（D）の `get_disclosed_memos` が「様子のメモ」（`memo`）の判断に使う（PR #44。spec 005 の `is_feature_disclosed(code)` と同じ形で、同じ開示設定のキャッシュを読む）
  - `get_active_replies(session, resident_id, date_from, date_to)`：保存された返事（返事は取り消せないので、保存されたものはすべて有効）
  **家族に出すもの（連絡帳・テーマのボタン・通知のまとめ・F の AI）は、必ずここの共通の関数を通す**。職員向け（記録の見返し・E の変化の検知）は、非開示の項目も含めて直接読んでよい。
  入居者 id は、呼び出す側がログイン中の家族から決めて渡す（家族が指定した値は使わない）。
- **理由**：非開示の記録が家族や AI に漏れないことを 1 か所で守れる（Constitution 原則 IV、SC-006）。記録の id を返すのは、F で「AI の回答がどの記録にもとづくか」を追跡するため（原則 III）。期間で取れると、AI が「最近」の質問に答えられる（AI 側で最大 7 日などに制限する）。記録した時刻は、20 時のまとめで「新しい記録があるか」を見るために使う。
- **ほかに考えた案**：各 API がそれぞれ開示設定を見て絞る（どこか 1 つで忘れると漏れる）。
- **未決定**：F の AI が職員の返事を読むか（案は「読んでよい。読む場合も `get_active_replies` を通す」。開発前MTG で決める）。

## R-07 最初に保存された返事だけを有効にする

- **決めたこと**：返事を保存するときに、`UPDATE requests SET status='answered' WHERE id=:id AND status='waiting'` を 1 回で行い、
  更新できた行が 0 件なら保存しない。そのときは、リクエストが `answered` なら「ほかの職員が返事をしました」、`cancelled` なら「このリクエストは取り消されました」と返す（409）。
  返事の行の追加と、この更新は 1 つのトランザクションで行う。
- **理由**：同時に返事したとき・取り消しとぶつかったときの両方を、ロックを使わずに 1 つの決まりで防げる（開発前MTG）。
- **ほかに考えた案**：`SELECT ... FOR UPDATE` で行をロックする（同じことができるが、書く量が増える）、Redis のロック（DB の中だけで済むことに、ほかの仕組みを足す必要がない）。

## R-08 返事待ちの上限（3 件・同じテーマ 1 件）

- **決めたこと**：同じテーマの返事待ちは、部分インデックスの一意制約（`resident_id, theme_id WHERE status='waiting'`）で DB が防ぐ。
  3 件の上限は、リクエストを作るトランザクションの中で家族アカウントの行を `FOR UPDATE` で押さえてから数える（DB の決まりとアプリ側の確認の両方で守る。開発前MTG）。
- **理由**：同時に 2 回押しても上限を超えない。同じテーマの重複は DB の決まりだけで確実に防げる。
- **ほかに考えた案**：数えてから追加するだけ（同時に押すと 4 件目が入る）。

## R-09 メールとアプリ内のお知らせの送り方

- **決めたこと**：
  - お知らせ（アプリ内）は `notifications` に、メールは送る予定として `email_outbox` に書く（アウトボックス）。メールを送る部品はさとこが作り、ようこが招待で使い回す。
  - **返事のお知らせ**は、ゆうの返事の保存処理が、さとこの `create_reply_notice(session, reply_id)`（`services/notifications.py`）を**同じ DB のセッションを渡して呼ぶ**。
    この関数の中では `commit` しない。返事の保存と同じトランザクションで確定するので、返事だけ保存されてお知らせが消える、ということが起きない。
    返事を直すときは呼ばない（再通知しない）。返事の取り消しはしない（FR-030）。
  - **決まった時刻の処理**（メールの送信・送り直し、20 時のまとめ（R-13）、前日の面会の知らせ（spec 003））は、1 つの関数 `run_jobs()`（`app/jobs/run.py`）にまとめ、**呼ばれたときに、その時点でやることを済ませる**。
    - 本番：外部のスケジューラー（cron-job.org）が **1 分ごと**に `POST /api/internal/jobs/run` を呼ぶ（[contracts/api.md](./contracts/api.md#決まった時刻の処理)）。1 分ごとに呼ばれるので、Render の無料のサービスもスリープしない。
    - 開発：`worker` のサービスが 1 分ごとに同じ `run_jobs()` を呼ぶ（開発と本番で、中身は同じ）。
  - `run_jobs()` は `email_outbox` の未送信を取り出して送り、送れたら `sent_at` を入れる。
    取り出すときは **`SELECT ... FOR UPDATE SKIP LOCKED`** で行を押さえ、呼び出しが重なっても、手で動かすコマンドと同時に動いても、同じメールを 2 回送らない。
    失敗したら回数を数え、5 回まで次の回で送り直す。1 回に送るのは数十件までにして、呼び出しが 30 秒以内に終わるようにする（cron-job.org の待ち時間）。
  - **返事・お知らせのメールは、保存したあとにその場でも送ってみる**：API が応答を返したあとに、FastAPI の BackgroundTasks で、さとこの `send_email_now(outbox_id)` を呼び、その行だけを同じく `FOR UPDATE SKIP LOCKED` で押さえて送る。
    `create_reply_notice` は作った `email_outbox` の id を返し、返事の API（ゆう）は、**返事の保存をコミットしたあとに** `send_email_now` を呼ぶ（コミットの前だと行がまだ見えない）。
    送れなかったときやプロセスが止まったときは、`email_outbox` に残っているので、次の `run_jobs()` で送られる（PR #34 ゆう・さとこ）。
  - 送り方は環境変数 `MAIL_TRANSPORT` で切り替える。開発は `smtp`（Mailpit。SMTP の 1025 番、画面は 8025 番）、本番は `resend`（Resend の API に https で POST する。キーは `RESEND_API_KEY`）。
    API を呼ぶ道具（Python 標準の `urllib.request` か、テストで使っている httpx2 を本番の依存にも入れるか）は、T057 を作るさとこが決める。ライブラリを本番の依存に足すときは、技術選定に理由を書く。
  - メールの文面は種類ごとのテンプレート（返事・今日のまとめ・今週のまとめ・施設からのお知らせ・招待）で作り、テンプレートに渡すのは**種類・タイトル（お知らせだけ）・アプリへのリンクだけ**にする。記録・返事・本文はテンプレートに渡さない。
    例外：spec 002 の `owner_account`（施設長のログイン用の ID を知らせるメール）だけは、ID を書くこと自体が目的なので `login_id` を渡す。パスワードは渡さない（spec 002 の research.md R-08）。
- **理由**：本番を置く Render の無料のプランでは、SMTP のポート（25・465・587）への外向きの通信が塞がれ、常に動き続ける worker（Background Worker）もなく、使われないと 15 分でスリープする。
  有料にしないため、本番は https で送り、決まった時刻の処理は外から呼ぶ形にした（[PRD](../../docs/PRD.md) 9 章の案 A、PR #28）。
  5 分以内（SC-010・SC-016）は、その場で送ることと、1 分ごとの送り直しで守れる。中身を渡さないことで、文面に中身が入る失敗を仕組みで防げる。
- **開発前MTG との違い**：開発前MTG の案では「返事の保存を確定したあとに `create_reply_notice(reply_id)` を呼び、失敗しても返事は取り消さない」だったが、
  PR #17 でさとこから「同じセッションを渡して呼び、関数の中では commit しない」という提案があり、こちらを採る。
- **ほかに考えた案**：API の中でその場で送る（メールサーバーが遅いと API も遅くなり、失敗したときに送り直せない）、FastAPI の BackgroundTasks だけで送る（プロセスが止まると送る予定が消える。今の形は、アウトボックスに残したうえで最初の 1 回だけに使う）、ジョブキュー（Celery など。ライブラリと覚えることが増える）、
  Render の有料のプランで worker を常に動かす（今の設計のまま使えるが、Background Worker は月 7 ドルから。PRD 9 章の案 B）、GitHub Actions の schedule で呼ぶ（5 分より短くできず、遅れることがある）。

## R-10 ファイルの保存先と配り方

- **決めたこと**：
  - お知らせの添付（毎月の献立表も、これで出す）・アルバムの写真は、`uploaded_files` の 1 つのテーブルと `services/uploads.py` の 1 つの処理で扱う。
  - 形式は、拡張子ではなく**ファイルの先頭のバイト**で確かめる（PDF は `%PDF-`、JPEG は `FF D8 FF`、PNG は `89 50 4E 47`）。10MB を超えたら受け付けない。
  - 画像は Pillow で開き直して保存し、Exif（位置情報など）を消す（作り込み）。
  - 保存先は、開発（とミニマム版）はコンテナのボリューム（`/data/uploads`）、本番は S3 互換のオブジェクトストレージ（Cloudflare R2 など。非公開のバケット）。どちらも `uploads.py` の中で切り替え、ほかの人は意識しない。
  - ファイルは**公開 URL を持たない**。`GET /api/files/{id}` が、ログインしていること・そのファイルを見てよい役割か・取り消されていないかを確かめてから返す。
    返すときは `Content-Type` を保存した形式に固定し、`X-Content-Type-Options: nosniff` を付ける（形式を偽ったファイルを画面の一部として実行させない。FR-025）。
  - **PDF の表示**：`Content-Security-Policy: sandbox` を付けると、ブラウザの PDF ビューアが表示しないことがある（PR #17 さとこ・ようこ）。
    そのため PDF には `sandbox` を付けない。Day 3 に、架空の PDF を iPhone の Safari と Android の Chrome で、別タブと画面の中の両方で開けるかを確かめ、
    表示できない環境があれば、PDF は `Content-Disposition: attachment`（ダウンロードして開く）にする。
- **理由**：「URL を知っていてもログインしていなければ開けない」（FR-034）を確実に守れる。形式のチェックと Exif の削除を 1 か所にまとめると、アルバム（H）でも使い回せる（spec 001 の Assumptions）。
- **ほかに考えた案**：署名付き URL（期限つきの公開 URL。漏れると期限まで誰でも開ける）、python-magic で形式を調べる（3 形式だけなら先頭のバイトで十分で、ライブラリを増やさずに済む）。
- **増えるライブラリ**：Pillow（画像の読み書きの定番。Exif を消すのは開いて保存し直すだけで、10 日間で使える）。

## R-11 多言語とふりがな

- **決めたこと**：
  - 文言は react-i18next の辞書（`ja.json`・`id.json`・`en.json`）に置く。表示言語は、ログイン中のアカウントの言語で決める。
  - 日本語の辞書では、ふりがなを `{漢字|かんじ}` の書き方で書く（例：`"{全部|ぜんぶ}（8{割|わり}）"`）。
    画面では `Ruby` の部品がこれを `<ruby>` に変えて表示する。インドネシア語・英語の辞書にはこの書き方を使わない（ふりがなが出ない）。
  - メールの文面では、`{漢字|かんじ}` を漢字だけにして出す（画面の外ではふりがなを付けられないため。FR-021）。
  - 家族の画面（`/family` の下）では、辞書は分けずに同じ `{漢字|かんじ}` の書き方のまま、家族の画面の枠でふりがなを出さないようにする（Constitution 3.2.0 の UI 方針の例外。#260）。職員の画面と家族の画面で同じ文言（エラーの文言など）を使っても、出し分けられるため。
  - 記録の値・テーマ・定型文は、DB には**コード**（`smile`、`theme.daily_life`、`template.daily_life.smile` など）で持ち、表示するときに辞書で引く。
    日本語はゆう、インドネシア語・英語はみさきが辞書に書く（開発前MTG の初期データの担当）。
  - 職員が自由に書いた短い文、お知らせの本文、ファイルの中身は、辞書を通さずそのまま出す（ふりがな・翻訳の対象外）。
  - ミニマム版では日本語だけ・ふりがななしで作り（作業分担MTG のミニマム版のルール）、辞書に文言を入れる形だけは最初から守る。
- **理由**：ふりがなを辞書の中に一緒に書けば、文言を足す人が読みも同時に書くので付け忘れが減る（SC-011 は、辞書の日本語に `{|}` のない漢字が残っていないかを調べるテストで確かめられる）。
- **ほかに考えた案**：形態素解析でふりがなを自動で付ける（読みの間違いが出るうえ、ライブラリが大きい）、ふりがなを別の辞書に分ける（文言と読みがずれやすい）。

## R-12 Redis の使い道（課題要件のキャッシュサーバー）

- **決めたこと**：Redis の接続の土台はようこが作り、使い道ごとに使う人が担当する。キーには用途ごとの接頭辞を付け、**必ず有効期限（TTL）を付ける**。

  | 使い道 | キー | 担当 | 時期 |
  |---|---|---|---|
  | ログインのセッション | `session:<ランダムなID>` | ようこ | ミニマム版（Day 2） |
  | 開示設定のキャッシュ | `cache:disclosure:<施設ID>`（期限 5 分） | ゆう | ミニマム版（共通の関数 3 つと一緒に作る） |
  | AI 問い合わせの回数制限 | `ratelimit:inquiry:<家族ID>:<日付>` | みさき | F の spec で決める |
  | ログインの試行回数の制限 | `ratelimit:login:<ID>` | ようこ | 作り込み（R-03） |

  - **家族の連絡帳（組み立て結果）はキャッシュしない**（[開発前MTG](../../docs/context/meeting/開発前MTG.md) の決定事項・PR #19）。
  - 開示設定は、共通の関数 3 つ（R-06）の中でキャッシュから読み、**開示設定を保存したらそのキャッシュを必ず消す**。消し忘れに備えて期限（5 分）も付ける。
    期限の長さが「消し忘れたときに、非開示の項目が見えてしまう最長の時間」になるので短くする。開示設定は数行なので、DB から読み直しても負担はほぼない（PR #17 ゆう、開発前MTG の決定事項）。
  - セッションの ID は、ユーザーの ID ではなく推測できないランダムな値にする。
  - セッションとキャッシュを同じ Redis に入れるので、いっぱいになったときに消す対象は**期限のあるキーだけ**（`maxmemory-policy volatile-lru`）にする。
  - 面会予約（G）で Redis のロックを使う場合も、二重予約を最後に防ぐのは DB の一意制約にする（G の spec で決める）。
- **理由**：連絡帳は、記録の保存・押し直し・取り消し、返事の保存・修正、返事の既読、開示設定の変更のどれでも変わり、
  どこかで消し忘れると、取り消した記録や非開示の項目が家族に見えてしまう（Constitution 原則 IV）。入居者 30 人の規模では、毎回 DB から組み立てても遅さは問題にならない。
  開示設定は変わる回数が少なく、消すのは設定を保存するときの 1 か所で済む。
- **ほかに考えた案**：連絡帳の組み立て結果をキャッシュする（上の理由で採らない）、セッションだけに使う（課題要件の「キャッシュ」としての説明が弱い）。

## R-13 1 日 1 回・1 週間に 1 回のまとめ

- **決めたこと**：`run_jobs()`（R-09）が、日本時間で 20:00 を過ぎて最初に呼ばれたときに、頻度が「1 日 1 回」の家族ごとに、前回のまとめのあと〜20:00 までに入った開示済みの記録（`get_disclosed_records` を通す）があるかを調べ、あればまとめのお知らせとメールを作る。
  日曜は「1 週間に 1 回」の家族の分も作る。どの家族のどのまとめを作ったかを `digest_runs`（家族×種類×期間で一意）に残し、**同じまとめを 2 回送らない**（20 時台は 1 分ごとに呼ばれるが、2 回目からは作らない）。
  まとめの締めは、呼ばれた時刻ではなく **20:00**。20:00 より後に入った記録は、次のまとめに入る。
  20:00 のあとしばらく呼ばれなかったときは、次に呼ばれたときに、その日（日本時間で 24 時までに）の分だけを作る。それより古い分は作らない（次のまとめに入る）。
- **理由**：一意の記録を残すことで、何度呼ばれても、呼び出しが遅れても、手で動かすコマンドと重なっても 1 回だけになる（SC-010）。時刻を見るのは `run_jobs()` の中だけなので、開発（worker が呼ぶ）と本番（外から呼ぶ）で動きが同じ。
- **ほかに考えた案**：Render の Cron Job を使う（無料のプランにはない）、外部のスケジューラーを 20:00 ちょうどにだけ呼ぶ（呼び出しに失敗したときに取り戻せない）。

## R-14 時刻と「当日」

- **決めたこと**：DB には UTC で保存し、「当日中の取り消し・修正」「20 時のまとめ」「日曜」は Asia/Tokyo で判断する（開発前MTG で決まったこと）。判断はバックエンドだけで行い、フロントの時計は使わない。
- **理由**：タブレットの時計がずれていても、取り消せるかどうかが変わらない。

## R-15 5 分以内の反映と既読

- **決めたこと**：
  - 家族の連絡帳は、画面を開いたとき・画面に戻ったときに API から読み直す（TanStack Query の `refetchOnWindowFocus`）。リアルタイムの配信（WebSocket など）は使わない。
  - 返事の既読は、連絡帳（ホーム）で**返事のカードが画面に出たら、フロントが自動で** `POST /api/family/replies/{id}/read` を呼ぶ。
    まだ読んでいない返事は、日付に関わらず一番上に出す（PR #17 さとこ）。
- **理由**：開いたときに最新を読めば 5 分以内（SC-008）を満たせる。既読のボタンを家族に押させないので、手間が増えない。

## R-16 API の型の共有

- **決めたこと**：FastAPI が出す OpenAPI（`/openapi.json`）から、`openapi-typescript` でフロントの型を作る。API を変えたら型を作り直してコミットする。
- **理由**：言語が 2 つでも、API の形のずれをコンパイルのときに見つけられる（技術選定のリスクと対応）。
- **増えるライブラリ**：openapi-typescript（型を作るだけのコマンドで、アプリの動きには入らない）。
- **今の状態（10/23・#62）**：openapi-typescript の最新版（7.13.0）は TypeScript 5 にしか対応しておらず（peerDependencies が `typescript: ^5.x`）、私たちの TypeScript 6 では `npm ci` がぶつかる。対応した版が出るまで入れず、それまでは使う人が必要な型を手で書く（例：`frontend/src/auth/me.ts` の `Me`）。TypeScript 6 に対応した別のもの（`@hey-api/openapi-ts`）もあるが、技術選定を変えることになるので、入れるならチームで決める。

## R-17 マイグレーション

- **決めたこと**：Alembic を使う。マイグレーションを作る直前に必ず main を取り込む。共通のテーブルはようこが Day 1 の午前に作り、ほかは各自の機能の PR で足す。
  同時に開いている 2 つの PR がそれぞれマイグレーションを足すと、マージしたあとに head が 2 つになるので、**CI で `alembic heads` が 1 つであることを確かめ**、
  ぶつかったら後からマージする人が直す（開発前MTG・PR #17 ようこ）。CI には PostgreSQL のコンテナを足す（ようこ）。
- **理由**：head が 2 つのままだと `alembic upgrade head` が失敗し、全員の環境が動かなくなる。
- **増えるライブラリ**：Alembic（SQLAlchemy の公式のマイグレーションの道具）。

## R-18 ログ

- **決めたこと**：structlog。開発は読みやすい形式で詳しく、本番は JSON で INFO 以上。氏名・メールアドレス・記録の値・返事の文・お知らせの本文・招待のトークンはログに出さず、id だけを出す（FR-027）。
- **理由**：技術選定で決まった方式。中身を出さないことを、ログを書くときの決まりにする。

## R-19 テスト

- **決めたこと**：
  - バックエンド：pytest ＋ httpx2 で API を呼ぶテスト。テスト用の PostgreSQL と Redis をコンテナで立てる（モックにすると、期限や一意制約が正しく動くかを確かめられないため）。特に次を確かめる。
    - 非開示が出ないこと（SC-006）、ほかの入居者が見られないこと（FR-020）
    - **ほかの家族の返事・リクエスト・お知らせの id を指定しても、読めない・操作できないこと**（id は連番で推測できるため。PR #17 ようこ）
    - 同時に返事したとき（R-07）、同じまとめを 2 回送らないこと（R-13）、メールの文面に中身が入らないこと（SC-010）
    - **本番の設定で、開発用のユーザー切り替えが 404 になること**（R-02）
  - テストの DB と Redis（#63）：CI は、ジョブの中で PostgreSQL・Redis のコンテナを立て、マイグレーションを当ててから動かす。
    手元は、開発の DB をそのまま使い、テストごとにトランザクションを取り消す（データは残らない。施設は初期データのものを使う）。
    Redis はテスト用の 15 番を使い、テストの前後で空にする（開発のログインの 0 番は消さない）。
    DB・Redis がないとき、手元では飛ばし、CI では失敗にする。準備は `backend/tests/conftest.py` にまとめる
  - フロントエンド：Vitest。`Ruby` の部品と、辞書の日本語にふりがなのない漢字が残っていないか（SC-011）。
  - E2E：Playwright で、quickstart.md の通しの流れ（記録 → 開示 → 頼む → 返事 → メール）を確かめる。
    動かし方：`docker compose up -d`（マイグレーションと初期データのあと）、`docker compose --profile e2e run --rm e2e`（quickstart.md）。開発の DB と開発用のユーザー切り替え（R-02）を使う。CI には、通し（T091b）がそろってから足すかを決める（仕組みだけの間は入れない）。
- **理由**：課題要件（単体テストはコード、結合・総合は テスト設計書）と、各 spec の受け入れシナリオをテストシナリオの元にする決まり（Constitution）。
