# Research: spec 005（アルバム）

調べて決めたこと。土台は [spec 001 の research.md](../001-family-priority-report/research.md)（R-09 お知らせとメール、R-10 ファイル、R-12 Redis、R-13 まとめ、R-14 時刻）。
新しく決めるのは、写真ならではの部分だけにする。

## R-01 写真の載せ方（1 枚ずつ送る）

- **決めたこと**：
  - 職員の画面は、「📷 撮る」（端末のカメラを開く）と「🖼 写真から選ぶ」（複数枚を選べる。10 枚まで）の 2 つのボタンを置く。
    どちらも、ファイルを選ぶ入力欄（`<input type="file" accept="image/jpeg,image/png">`）で足りる。カメラは `capture="environment"` を付けた入力欄で開く。
  - 選んだ写真は、画面にプレビューを出し、写真ごとに一言コメント（任意・100 文字まで）の欄を置く。
  - 送るのは **1 枚ずつ**（`POST /api/staff/residents/{id}/album`、`multipart/form-data` に写真 1 枚とコメント）。画面が順番に送り、枚数と成功・失敗を表示する。
    失敗した写真だけ「もう一度送る」ボタンを出す。
  - 画面でも 10MB を超える写真は送る前に断る（サーバー側でも断る。FR-003）。
- **理由**：1 回で 10 枚（最大 100MB）を送ると、途中で通信が切れたときに全部やり直しになる。1 枚ずつなら、切れた分だけ送り直せる（Edge Cases の「通信が途中で切れた」）。
  カメラを開く入力欄は複数枚を選べないため、「撮る」と「選ぶ」を分ける。
- **ほかに考えた案**：10 枚をまとめて 1 リクエストで送る（切れたときの扱いが難しい）、アプリ専用のカメラ画面を作る（ライブラリが増える。10 日間では不要）。

## R-02 写真の処理（形式）

- **決めたこと**：
  - 形式の確認（先頭のバイト。JPEG は `FF D8 FF`、PNG は `89 50 4E 47`）、10MB まで、保存は、spec 001 R-10 の `services/uploads.py` をそのまま使う。**アルバムでは PDF を受け付けない**（`allowed_types` を呼び出し側が渡す形にする）。
  - **Pillow は使わない**（Session 2026-10-28。#146 をやらないことにしたため）。Exif の除去・向きの直し（`exif_transpose`）・サムネイル・画素数の上限・アニメーション PNG や壊れた画像の拒否は、やらない。写真は加工せずに保存する。
  - 向きは、ブラウザが写真の向きの情報（Exif）を見て、正しい向きで表示する（実機での確認は、これから）。
- **理由**：Pillow を足さない決定（spec 001 の R-10）に合わせる。一覧は、元の写真を `loading="lazy"`（画面に出るときに読む）で出す。デモの枚数なら足りる。位置情報が写真に残る可能性は承知のうえで、デモは架空の写真だけを使う。
- **ほかに考えた案**：サムネイルと向きの直しのためだけに Pillow を足す（ライブラリが増える。チームで、足さないと決めた）、元の写真を縮小して保存する（家族が大きく見たいときに画質が落ちる）、ブラウザの側で縮小してから送る（端末ごとに扱いが違い、サーバー側で確かめ直す必要がある）。

## R-03 家族に出す道は 1 つだけ

- **決めたこと**：
  - 家族に写真を見せる処理は、`services/album.py` の `get_visible_album_photos(resident_id, before=None, limit=12)` の 1 つだけにする。
    この関数は、(1) 開示設定でアルバムが「見せる」か、(2) その入居者の写真か、(3) 削除されていないか、を確かめて返す。
  - 家族のアルバムの一覧 API も、写真のファイルを返す `GET /api/files/{id}`（アルバムの写真のとき）も、同じ条件を通る。
    ファイルの API は、`album_photos` を `file_id` で引き、`get_visible_album_photos` と同じ判定の関数 `can_family_view_photo(photo, resident_id)` を使う。
  - 条件に合わないとき（ほかの入居者の写真・削除された写真・アルバムを見せない設定）は、**404 `not_found`**（存在するかどうかも知らせない。spec 001 と同じ）。ログインしていなければ 401。
  - 職員は、どの入居者の写真も開ける（削除された写真は除く）。
- **理由**：spec 001 の「家族に出すものは共通の関数を通す」（R-06）と同じ考え方。一覧とファイルで判定が分かれると、片方だけ抜けて、URL から他の入居者の写真が見えてしまう。
- **ほかに考えた案**：一覧の API だけで確かめ、ファイルは `storage_key` を知らなければ開けないことに頼る（推測されにくいが、URL が漏れると開けてしまう。FR-007 を守れない）。

## R-04 開示設定の「アルバム」

- **決めたこと**：
  - `disclosure_settings` の `target_type` に **`feature`** を足し、`target_code = 'album'`、初期値 `visible = true` の行を 1 つ持つ（FR-013）。
    記録項目（`item`）やテーマ（`theme`）とは別の種類にして、`get_disclosed_records` の項目や通知の選択肢（`notify_items`）に混ざらないようにする。
  - `services/disclosure.py`（ゆう）に `is_feature_disclosed(code)` を足す。開示設定のキャッシュ（`cache:disclosure:<施設ID>`）を読み、保存時にキャッシュを消す今の仕組みをそのまま使う。
  - `GET /api/admin/disclosure`・`PUT /api/admin/disclosure`・変更履歴（`disclosure_setting_histories`）は、`feature` の行も同じように扱う（FR-015）。
  - 家族のメニュー（「☰ その他」）にアルバムを出すかは、家族の画面の枠が呼ぶ API `GET /api/family/features`（新規。`{ "album": true }` のように、開示設定の `feature` の状態だけを返す）で決める。
- **理由**：開示設定の画面・履歴・キャッシュの消し方が、そのまま使える。作る量が最も少ない。
- **ほかに考えた案**：`item` の 1 つ（`album`）として入れる（`get_disclosed_records` や通知の項目に混ざらないよう除外する処理が要る）、別のテーブルを作る（履歴の仕組みを作り直すことになる）。
- **ゆうと確かめること**：`feature` の行を足す（`target_type` の値を増やす）ことと、`is_feature_disclosed` を足すこと。

## R-05 写真の削除

- **決めたこと**：
  - 職員（介護職員・リーダー・生活相談員・施設長）が `DELETE /api/staff/album/{id}` で削除する。家族は削除できない（403）。画面では確認を出す。
  - 削除は次の順で行う。
    1. 1 つのトランザクションで、`album_photos` に `deleted_by`・`deleted_at` を入れ、`file_id`・`comment` を空にし、`uploaded_files` の 1 行（元の写真）を消す。ここで、家族の一覧からもファイルの URL からも見えなくなる。
    2. そのあと、保存先のファイル 1 つを消す。消せなかったときは、`storage_key` の id をログに出す（写真そのものは URL から開けない状態になっているので、残ったファイルは誰にも配られない）。
  - 履歴には「誰がいつ削除したか」だけを残し、写真・コメントは残さない（FR-012）。
- **理由**：先に家族の画面から外すことで、「消したのにまだ見える」時間をなくす。保存先のファイルが残ってしまう失敗より、家族に見え続ける失敗のほうが重い。
- **ほかに考えた案**：保存先のファイルを先に消す（データベースの更新が失敗したとき、写真が壊れた状態で残る）、削除後も一定期間ファイルを残す（SC-005 を満たせない）。

## R-06 新しい写真の通知（まとめに足す）

- **決めたこと**：
  - 通知は新しい種類を作らず、**spec 001 のまとめ（`daily_digest`・`weekly_digest`）に「写真あり」を足す**（FR-018）。
  - `notifications` に `has_album`（boolean、初期値 `false`）と `has_records`（boolean、初期値 `true`）を足す。`digest.py` が家族ごとのまとめを作るとき、次を調べる。
    - 記録：`get_disclosed_records`（今までどおり。開示済み・通知する項目だけ）
    - 写真：`album_photos` のうち、前回のまとめのあと〜今回の 20:00 までに載せられ、削除されておらず、アルバムが「見せる」で、家族が「アルバムの新しい写真」を通知する設定にしているもの
    - 記録も写真も 0 件なら送らない。どちらかあれば 1 通のまとめを作り、写真があるときは `has_album = true` にする。記録があるときは `has_records = true`（記録が 0 件のときは `false`）にする。
  - 家族が選べる通知の内容に「アルバムの新しい写真」を足す（`notification_settings.notify_album`、初期値 `true`）。アルバムを見せない設定のときは、選択肢に出さない。
  - まとめの文面は、固定の文言を辞書から引く：記録だけ「今日の連絡帳がまとまりました」、写真だけ「アルバムに新しい写真が載りました」、両方「今日の連絡帳がまとまりました。アルバムに新しい写真が載りました」。
    メールのテンプレートには `has_album`・`has_records`（真偽）と、アプリへのリンクだけを渡す。**写真・ファイル名・コメント・入居者名は渡さない**（FR-019）。
  - 同じまとめを 2 回送らない仕組み（`digest_runs`）は、そのまま使う。
  - 「アルバムの新しい写真」をオフにしている間に載った写真は、その間のまとめには入らない。ただし、まとめの期間の始まりは「前回に作ったまとめの締め」なので、オンに戻した次のまとめで、オフの間に載った写真もまとめて知らされる（記録の通知と同じ考え方。オフの間の分を、あとから知らせなくする処理は作らない）。
- **理由**：載せるたびに送ると、1 日に何回も通知が届いて嫌がられる（spec 001 の決定と同じ）。まとめに足すだけなので、worker・`digest_runs`・メールのテンプレートを作り直さずに済む。
- **ほかに考えた案**：アルバム専用のまとめ（`album_digest`）を別に作る（家族のメールが 1 日 2 通になる。`digest_runs` の種類も増える）。

## R-07 家族のアルバムの一覧の出し方

- **決めたこと**：
  - 載せた日（日本時間）ごとにまとめ、新しい日を上にして返す。1 回の API で、新しい順に 12 枚（既定。`limit` の上限は 30。サムネイルがなく、1 枚 3〜8MB ほどなので、最初の読み込みを軽くする。Session 2026-10-28）。続きは `before`（前回の最後の `posted_at` と id）で読む「もっと見る」方式にする。
  - 一覧には、元の写真の URL（`/api/files/{file_id}`）を返す（サムネイルはない。Session 2026-10-28）。
  - 写真がまだないときは、空の配列を返し、画面で「まだ写真はありません」を出す。
  - コメントはそのまま返す（辞書を通さない。画面では文字としてのみ表示する）。
- **理由**：過去の写真をすべて見られる（FR-005）ので、一度に全部は返さない。30 人・1 日数十枚なら、続きを読む方式で十分。

## R-08 テスト

- **決めたこと**：
  - pytest：他の入居者の写真を一覧・ファイルの両方で 404、ログインなしは 401、JPG・PNG 以外と 10MB 超は `invalid_file`、名前だけ JPG の PDF は拒否、
    削除後は 404 でファイルも消える、アルバムを見せない設定にすると一覧・ファイルが 404 になり「見せる」に戻すと見られる、
    まとめに写真が 1 回だけ入る（2 回動かしても増えない）、削除した写真はまとめに入らない、メールに写真・コメント・入居者名がない。
  - Vitest：載せる画面（プレビュー・コメント 100 文字・失敗した写真の再送）、アルバムの画面（日ごと・空の状態）。
  - Playwright：[quickstart.md](./quickstart.md) の通しの確認。
  - テスト用の写真は、架空の画像をテストの中で作る（`tests/helpers/images.py`。実在の人物の写真は使わない）。

## R-09 ログ

- **決めたこと**：ログには写真の id・入居者の id・職員の id・結果だけを出す。ファイル名、コメント、入居者名は出さない（spec 001 R-18 と同じ）。
