# Research: spec 002（J：システム利用料）

plan で決めたことと、その理由・ほかに考えた案。spec 001 の [research.md](../001-family-priority-report/research.md)（以下「001 の R-xx」）の決まりは、そのまま使う。
Stripe の仕組みは、Stripe の公式ドキュメント（Checkout・Billing・Webhooks・Customer Portal）にもとづく。

## R-01 決済サービスとのつなぎ方（Stripe Checkout ＋ Billing）

- **決めたこと**：
  - 支払いは **Stripe Checkout**（Stripe が用意する支払い画面）の `subscription` モードで行う。アプリはカード情報に一切触れない（FR-008）。
  - 月額のプランは、Stripe のテスト環境の管理画面で「商品」と「価格（月額 10,000 円）」を 1 つ作り、価格に **lookup key `monthly_standard`** を付ける。
    アプリは lookup key で価格を探す（価格の ID を環境変数に書かない。作り直しても ID を書き換えずに済む）。
  - 画面に出すプラン名と金額は、アプリの設定の定数（`PLAN_NAME`・`PLAN_AMOUNT_JPY`）から出す。Stripe 側の金額と食い違っていないかは quickstart で確かめる。
  - バックエンドは公式の Python ライブラリ `stripe` を使う。
- **理由**：カード情報を受け取らないことを、仕組みで守れる（SC-005）。月額の自動の請求・失敗したときの再請求・領収書は Stripe Billing に任せられる（spec の Assumptions）。
- **増えるライブラリ**：`stripe`（Stripe の公式ライブラリ。Python 3.13 で入り、既知の脆弱性がないことを確かめた。技術選定 7 章）。開発だけで Stripe CLI（Webhook を手元に転送する。R-11）。
- **ほかに考えた案**：Stripe Elements（アプリの画面にカードの入力欄を埋め込む。作る量が増え、カード情報がアプリの画面を通る）、Payment Links（Stripe の管理画面で作るリンク。申し込みとアカウントを結びつけにくい）。

## R-02 申し込みから「契約中」までの流れ

- **決めたこと**：

  ```text
  申し込みページ（ログインなし）
    → POST /api/billing/signup：入力を確かめ、申し込み（billing_applications）を 1 行作る（パスワードはここでハッシュにする）
    → Stripe の Checkout Session を作る（client_reference_id＝申し込みの ID、customer_email＝連絡用のメールアドレス）
    → 画面は Stripe の支払い画面へ移る
  支払い画面でカードを入れて払う
    → Stripe が Webhook（checkout.session.completed）を送る
    → POST /api/billing/webhook：署名を確かめる → 1 つのトランザクションで、施設・施設長のアカウント・契約を作り「契約中」にする
  Stripe が申し込み完了の画面に戻す（/signup/complete?session_id=...）
    → 画面は GET /api/billing/signup/complete を数秒ごとに読み、アカウントができたらログイン用の ID を出す（できるまでは「お支払いを確認しています」）
  ```

- **理由**：アカウントは Webhook を確かめたあとにだけ作る（FR-002・FR-009）。支払い画面から戻ってきたことだけでは作らない。戻ってきたときにまだ Webhook が届いていなくても、画面が読み直すので待てる（US1 のシナリオ 4）。
- **ほかに考えた案**：戻ってきたときに Checkout Session を Stripe から読んでアカウントを作る（Webhook と二重に作る道ができ、どちらが先でも 1 回だけ作る工夫がさらに要る）。

## R-03 Webhook の確かめ方と、同じ知らせ・順番の入れ替わり

- **決めたこと**：
  - Webhook の受け口 `POST /api/billing/webhook` は、**受け取った本文をそのまま**（JSON に直す前に）Stripe の署名の確認にかける。秘密は `STRIPE_WEBHOOK_SECRET`。確かめられなければ 400 を返し、契約は変えず、ログに残す（FR-010・SC-004）。
  - この受け口は、ログインと、書き込みの API の `X-Requested-With` の確認（001 の R-03、T014）の**対象から外す**。Stripe はこのヘッダーを付けないため。代わりに署名で確かめる。
  - **同じ知らせ**（FR-011）：受け取った知らせの ID を `billing_events` に一意で残す。すでにある ID なら、何もせずに 200 を返す。
  - **順番の入れ替わり**（FR-012）：知らせの中身の状態を信じず、知らせを受け取るたびに **Stripe から契約（Subscription）の今の状態を読み直して**、それに合わせる。
    古い知らせがあとから届いても、読み直した結果は今の状態なので、状態が戻らない。
  - 知らせの処理は、受け口の中で行う（速く終わる処理だけなので、worker に回さない）。失敗したら 500 を返し、Stripe の再送に任せる（Stripe は最大 3 日間、送り直す）。
- **扱う知らせ**：

  | 知らせ | すること | 時期 |
  |---|---|---|
  | `checkout.session.completed` | 申し込みページからの申し込み：施設・施設長・契約を作る（R-04）。申し込み直し：契約を結び直す | ミニマム |
  | `customer.subscription.created`・`updated`・`deleted` | 契約の状態を読み直して合わせる（R-05） | 作り込み（ミニマムでは completed だけで「契約中」にする） |
  | `invoice.payment_failed`・`invoice.paid` | 契約の状態を読み直して合わせる | 作り込み |
  | `checkout.session.expired` | 支払われなかった申し込みを消す（R-07） | ミニマム（行を消すだけなので軽い） |

- **理由**：Stripe は同じ知らせを 2 回以上送ることがあり、順番も保証しない（Stripe の Webhooks のドキュメント）。「読み直して合わせる」は、Stripe が勧めている方法で、順番を比べる工夫がいらない。
- **ほかに考えた案**：知らせの作られた時刻を比べて古いものを捨てる（同じ秒の知らせを比べられない）、worker で非同期に処理する（ミニマム版では作る量が増えるだけ）。

## R-04 施設と施設長のアカウントを作る処理

- **決めたこと**：`checkout.session.completed` を受けたら、1 つのトランザクションで次を行う。
  1. PostgreSQL の**アドバイザリーロック**（`pg_advisory_xact_lock`）で、施設を作る処理を 1 つずつにする
  2. 申し込みの行を `FOR UPDATE` で押さえる。すでに `completed` なら何もしない（同じ知らせが別の ID で来ても 1 回だけ）
  3. 施設がすでにあれば作らない。**その申し込みの Stripe の契約（Subscription）をすぐに解約し**（翌月から請求されないように）、申し込みを `rejected` にしてログに残す（FR-016。返金はシステム管理者が Stripe の管理画面で行う）
  4. Stripe の顧客の名前を施設名にする（Checkout では名前が入らないため。支払われた顧客だけに付けるので、使われない顧客に名前が残らない）
  5. `facilities`・`users`（`kind=staff`、ログイン用の ID、申し込みのときのパスワードのハッシュ）・`staff`（`role=director`）・`facility_subscriptions`（「契約中」）を作る
  6. 申し込みを `completed` にし、**パスワードのハッシュ・施設名・施設長の名前・メールアドレスを申し込みの行から消す**（施設・アカウントに移したので、個人情報を二重に持たない。`rejected` のときも消す）
  7. 作り込み：ID を書いたメールの送る予定を `email_outbox` に足す（R-08）
  - Stripe を呼ぶ操作（3 の解約、4 の顧客の名前）は、DB を確定する前に行う。失敗したら 500 を返し、Stripe の再送で処理し直す（DB はまだ確定していないので、やり直せる）。
  - 再送のときに同じ操作をしても困らないようにする：3 の解約は、Subscription を読み直してすでに `canceled` なら呼ばない（「すでに解約済み」のエラーも成功として扱う）。4 の顧客の名前は、同じ値で上書きするだけなので何度呼んでもよい。
    解約は成功したのに DB の確定だけが失敗したとき、再送で 500 を返し続けないため（PR #25 みさき）。
- **理由**：「施設は 1 つだけ」と「同じ知らせで 2 回作らない」を、DB の中で確実に守れる（SC-003）。ロックは施設を作るときだけなので、ほかの処理を待たせない。
  2 つ目の申し込みの契約を解約しないと、返金しても翌月から請求が続いてしまう（PR #25 みさき）。

## R-05 契約の状態

- **決めたこと**：アプリの状態は 4 つ（spec の FR-018）。Stripe の Subscription の状態から決める。

  | アプリの状態（コード） | 画面の文言 | Stripe の状態 |
  |---|---|---|
  | `active` | 契約中 | `active`（解約の予約なし） |
  | `payment_failed` | 支払いに失敗 | `past_due`・`unpaid` |
  | `cancel_scheduled` | 解約予定 | `active` で `cancel_at_period_end = true` |
  | `canceled` | 解約済み | `canceled`・`incomplete_expired` |
  | （変えない） | — | `incomplete`（最初の支払いの確認中）・`trialing`・`paused`（このアプリでは使わない）・表にないもの。今の状態のままにし、WARNING で状態のコードだけをログに出す |

  - 状態が変わったら `subscription_status_histories` に、いつ・どこから・どこへ・どの知らせで、を残す（FR-019）。
  - 初期データの施設は、Stripe とつながっていない「契約中」として作る（`stripe_customer_id` が空）。この施設では、次の請求日やカードの変更は出さない（spec の Assumptions）。
- **理由**：画面で使う区分だけに絞り、Stripe の細かい状態は対応表 1 か所で変える。

## R-06 ログイン用の ID の形と、パスワード（基盤と共通）

- **決めたこと（基盤の提案。spec 001 の T009・T088 と同じ形にする）**：
  - 職員のログイン用の ID は **`s` ＋ 5 桁の数字**（例：`s00001`）。PostgreSQL のシーケンスから順に作り、重ならない。施設長も事務員も介護職員も同じ形（spec 002 FR-003、開発前MTG の「職員の ID は付与する」）。
  - パスワードの決まりは、ログイン全体で共通にするため **spec 001 の research.md R-03** に書く（8〜64 文字・文字の種類の組み合わせは求めない・よく使われるパスワードを弾く）。申し込みページもそれに従う（spec の Assumptions）。
- **理由**：タブレットで打ちやすい短い形にする。ID の形をそろえると、ログインの画面と確かめ方が 1 つで済む。
- **ほかに考えた案**：ID を施設番号＋連番にする（施設は 1 つなので意味がない）、メールアドレスでログイン（職員は仕事用のメールアドレスを持っていないことが多い。001 の R-01）、
  パスワードの長さを 15 文字以上にする（NIST の第 4 版の基準どおりだが、職員の負担が大きい。001 の R-03）。

## R-07 支払われなかった申し込み・同時に 1 つだけ

- **決めたこと**：
  - Checkout Session の有効期限を **30 分**（Stripe で選べる最短）にする。期限が切れると Stripe が `checkout.session.expired` を送るので、その申し込みの行を消す（パスワードのハッシュも消える。FR-006）。
  - **支払い画面から「戻る」で戻ったとき**：Checkout の `cancel_url` を `/signup?canceled=1&key=<idempotency_key>` にする。画面は `POST /api/billing/signup/cancel` でその申し込みを取り消し、
    サーバーは Stripe でその Checkout Session を失効させて（`expire`）申し込みの行を消す。画面は保存していた `idempotency_key` を消して新しく作るので、入力を直して申し込み直せる。
    取り消すのは **`pending` の申し込みだけ**。`completed`・`rejected`・行がないときは何もせず 204 を返す（片方のタブで払い終えたあと、もう片方のタブで「戻る」を押しても、作ったアカウントの記録を消したり、支払い済みの画面を失効させようとしてエラーになったりしない。PR #25 みさき）。
  - 同時に 1 つだけ（FR-014、作り込み）：申し込みを作る前に、期限内で `pending` の申し込みがあれば 409（`signup_in_progress`）を返す。
    「戻る」で戻った本人は、上の取り消しで古い申し込みが消えているので、409 にならない（PR #25 みさき）。
- **理由**：期限を短くすると、放置された申し込みで本物の施設長が待たされる時間が短くなる（Edge Cases）。

## R-08 ID を書いたメール（作り込み。さとこの `email_outbox` を使う）

- **決めたこと**：
  - `email_outbox` のテンプレートに `owner_account` を足す。params は `{"login_id": "s00001", "link": "<ログイン画面の URL>"}`。パスワードは入れない（FR-005）。
  - 001 の R-09 では params に「種類・タイトル・リンクだけ」を入れる決まりだが、ログイン用の ID はメールに書くこと自体が目的なので、例外として params に入れる。
    params はログに出さない（001 の R-18。ログには `email_outbox` の id だけ）。
  - **1 通だけにする仕組み**：メールの送る予定は、R-04 のアカウントを作るトランザクションの中で足す。アカウントを作る処理が 1 回しか動かないので、メールも 1 通だけになる（SC-003）。
    そのため `email_outbox` に `dedupe_key` の列は足さない（さとこの T048 は変えない）。
- **理由**：同じ知らせが何回届いても、アカウントと同じ場所で 1 回だけ作れば、メールの側に重複を防ぐ仕組みを持たなくて済む。
- **さとこと確認すること**：テンプレート `owner_account` の追加と、params に `login_id` を入れる例外。

## R-09 施設長の連絡用メールアドレスの置き場所

- **決めたこと**：`facilities.billing_email` に置く（「利用料について連絡するアドレス」）。Stripe の顧客のメールアドレスと同じ。ID を書いたメールもここに送る。
- **理由**：`users.email` は家族がログインに使う一意の列なので、ログインに使わず一意でもない施設長のアドレス（FR-003）を入れると、意味が混ざる。
  利用料の連絡先は施設に 1 つあればよい。
- **ほかに考えた案**：`staff` に `contact_email` を足す（職員ごとに持つ必要がない）、`users.email` に入れる（上の理由で採らない）。

## R-10 申し込み直しとカードの変更・解約

- **申し込み直し（解約済み。作り込み）**：管理画面の「申し込む」で、施設の Stripe の顧客（`stripe_customer_id`）に対して Checkout Session を作る。
  開いている支払い画面があれば、それを返す（施設長と事務員が同時に押しても同じ画面。FR-013）。契約中なら 409（`already_subscribed`。US1 のシナリオ 8）。
- **カードの変更・解約・請求の履歴（US3、作り込み）**：Stripe の **Customer Portal** のセッションを作り、その URL へ移す。Portal で選べることは、Stripe の管理画面で「カードの変更・解約（期間の終わりに）・請求の履歴」に絞る。
- **理由**：画面を作らずに、領収書まで Stripe に任せられる（spec の Assumptions）。

## R-11 開発での動かし方とテスト

- **決めたこと**：
  - 鍵は `.env` に置く：`STRIPE_SECRET_KEY`（テスト環境の鍵）、`STRIPE_WEBHOOK_SECRET`。キー名は `env.example` に足す（FR-022）。
    作り込みで、必要な操作だけができる「制限付きの鍵」に替え、差し替えの手順を quickstart に書く（FR-026）。
  - Webhook は、**Stripe CLI** のコンテナ（`stripe/stripe-cli`）で手元の backend に転送する。docker-compose.yml に `stripe` の profile で足す（決済を試すときだけ起動）。
  - **自動テストでは Stripe を呼ばない**（CLAUDE.md）。Stripe のライブラリの呼び出しはモックにし、Webhook のテストは、テスト用の秘密で署名を作って送る。
    確かめること：署名が違うと 400 で状態が変わらない（SC-004）、同じ知らせを 3 回送っても施設・アカウント・契約・履歴・メールが 1 つ（SC-003）、
    「解約」のあとの古い「支払い完了」で状態が戻らない（SC-008）、二度押しで申し込みと支払い画面が 1 つ（SC-009）、DB・ログにカード番号とパスワードが残らない（SC-005・SC-007）。
- **理由**：テスト用の環境の鍵を CI に置かずに済み、テストが外の通信で落ちない。

## R-12 二度押し（FR-013・SC-009）

- **決めたこと**：
  - 申し込みページは、ランダムな値（`idempotency_key`）を作ってブラウザの `localStorage` に残し、送るたびに同じ値を付ける（2 つのタブでも同じ値になる）。
    申し込みが終わったとき・「戻る」で取り消したとき（R-07）に消す。`localStorage` が使えないときは、画面を開いている間だけ同じ値を使う。
  - バックエンドは、同じ値の申し込みがあれば、新しく作らずに同じ支払い画面の URL を返す（`billing_applications.idempotency_key` は一意）。
    同じ値の申し込みがあっても期限（`expires_at`）が過ぎていれば（`checkout.session.expired` がまだ届いていないとき）、その行を消して作り直す。ボタンは押したらすぐ押せなくする。
  - **Stripe に渡す冪等キーは `signup-<申し込みの id>`**（申し込みの行ごとに別のキー）にする。Stripe の冪等キーは、同じキーで中身も同じときだけ同じ結果を返し、中身が違うと `idempotency_error` になる。
    Checkout の `expires_at` は頼むたびに変わり、Stripe はキーを 24 時間覚えているので、ブラウザの値をそのまま渡すと、期限切れのあとの申し込み直しがエラーになる（PR #25 みさき）。
    Stripe の冪等キーは、ライブラリが通信の失敗で自動で送り直すときに、同じ支払い画面が 2 つできないようにするために使う。
  - **同じ値がほぼ同時に 2 つ届いたとき**：1 つ目は、申し込みの行を足してから Stripe を呼び、`checkout_url` を書いて確定する（ここまで 1 つのトランザクション）。
    2 つ目の行の追加（`INSERT ... ON CONFLICT DO NOTHING`）は、PostgreSQL が 1 つ目の確定を待たせるので、待ったあとに行を読み直して、その `checkout_url` を返す。Stripe には頼み直さない。
    1 つ目が失敗して行が残らなかったときは、2 つ目がそのまま申し込みを作る。どちらも 500 にはしない（PR #25 みさき）。
- **理由**：二度押し・2 つのタブ・同時に届いたとき・期限切れのあとの申し込み直しのどれでも、申し込みと支払い画面が 1 つになり、Stripe のエラーにもならない。
  Stripe を呼ぶあいだトランザクションを開いたままにするが、申し込みは施設に 1 つの頻度なので、待つのは同じ値の 2 つ目だけになる。
  Stripe の応答が遅いときに接続をつかみ続けないよう、Stripe を呼ぶときの待ち時間に上限（10 秒）を付ける（T010）。超えたら申し込みを消して 502。
- **ほかに考えた案**：
  - 2 つ目が同じキーで Stripe に頼み直す（`expires_at` が変わるのでエラーになる）
  - 1 つ目の行の `expires_at` を使って頼み直す（中身をそろえ続ける必要があり、壊れやすい。期限切れで行が消えたあとの申し込み直しは解決しない）
  - 先に行を「作成中」で確定してから Stripe を呼び、2 つ目は URL が入るまで読み直す（トランザクションは短いが、読み直しの処理と、途中で落ちて URL のない行の片付けを自前で書く）
  - 2 つ目には「処理中」の 409 を返し、画面が送り直す（サーバーは簡単だが、画面に送り直しの処理が要る）
  - 支払い画面の期限を付けない（中身が毎回同じになるが、期限が 24 時間になり、R-07 の 30 分と食い違う）

## R-13 ログ

- **決めたこと**：001 の R-18 に従う。決済では、申し込みの id・施設の id・Stripe の知らせの id と種類・状態のコードだけを出す。
  施設名・名前・メールアドレス・パスワード・カードの情報・鍵は出さない（FR-023）。署名を確かめられなかった知らせは、WARNING で「確かめられなかった」ことだけを出す。
