# Quickstart: spec 002 の動かし方と、通しの確認

決済（J）ができているかを、手で通して確かめる手順。Day 3 の通しのデモと、テストシナリオ（`docs/テスト設計書.md`）の元にする。
API は [contracts/api.md](./contracts/api.md)、テーブルは [data-model.md](./data-model.md)、理由は [research.md](./research.md) を見る。

## 用意するもの（最初の 1 回だけ）

1. Stripe のアカウントで、**テスト環境（サンドボックス）** を使う。本番の環境は使わない（FR-024）。
2. テスト環境の管理画面で、商品「月額プラン」と、価格「月額 10,000 円（JPY・毎月）」を作り、価格の **lookup key を `monthly_standard`** にする（R-01）。
3. テスト環境の秘密の鍵を、`.env` の `STRIPE_SECRET_KEY` に入れる（チャット・コード・PR に貼らない）。
4. 作り込み（US3）では、Customer Portal の設定で「カードの変更・解約（期間の終わりに）・請求の履歴」だけを有効にする（R-10）。
5. 作り込み（US2）では、テスト環境の管理画面の「設定 → Billing → サブスクリプションとメール通知」で、「カード決済が失敗した場合にメールを送信」をオンにする（FR-021。アプリからは送らない。T036）。

### 利用料の画面で「次の請求日」を見るには

初期データの施設は Stripe とつながっていない（`stripe_customer_id` が空）ので、次の請求日は出ない（R-05）。
次の請求日・支払い失敗・解約予定の表示は、**申し込みページから本物の申し込みを通して作った施設**でログインして確かめる。
申し込みページは施設がないときだけ開けるので、空の DB（初期データを入れる前）で申し込む。デモもこの順で行う（spec.md の Clarifications）。

## 起動

```bash
docker compose up -d
docker compose exec backend alembic upgrade head
docker compose --profile stripe up -d stripe   # Stripe CLI。Webhook を backend に転送する（R-11）
docker compose logs stripe                     # 表示された whsec_... を .env の STRIPE_WEBHOOK_SECRET に入れ、backend を再起動する
```

**空の DB から始める**（申し込みページは、施設がまだないときだけ開ける。spec の Assumptions）。

## ぶつかる場面・守りの確認

| すること | こうなれば OK | spec |

| 支払い画面で「戻る」 | 「お申し込みは完了していません」。施設もアカウントもできない。入力を直して、すぐにもう一度申し込める | US1 のシナリオ 3・R-07 |

| 署名のない知らせを、`curl -X POST http://localhost:8000/api/billing/webhook -d '{}'` で backend に直接送る | 400。契約の状態は変わらない | SC-004 |
| Stripe の管理画面の「Webhook のイベント」から、同じ知らせを再送する | 施設・アカウント・契約・履歴は増えない | SC-003 |

| Stripe の管理画面で顧客を開く | 施設名とメールアドレスだけで、入居者・家族の情報はない | FR-025・SC-010 |

## テストを動かす

```bash
docker compose exec backend python -m pytest tests/api/test_billing*.py
```

Stripe はモックにするので、鍵がなくても動く（CLAUDE.md の「自動テストでは Stripe をモックにする」）。
