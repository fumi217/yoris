# Feature Specification: 施設がアプリの月額利用料を支払う（J：システム利用料）

**Feature Branch**: `docs/spec-002-billing`

**Created**: 2026-10-20

**Status**: Draft

**Input**: User description: "施設（施設長）が、アプリ会社にアプリの月額利用料を Stripe で支払う。施設は1つの前提。Stripe Billing のテストモードを使い、実課金はしない。施設長は管理画面から Checkout で申し込み、支払いが終わると、Stripe の Webhook（署名を検証する）で施設の契約状態が「契約中」になり、管理画面で契約状態を確かめられる。ミニマム版（Day 3）は「テスト用カードで1回払えて、契約中になる」まで。未確定：支払いできる役割（施設長だけか、事務員も含むか）、料金プランの数と金額、カードの変更や解約（顧客ポータル）をどこまで作るか、未払い・支払い失敗・解約のときにアプリの利用をどうするか（家族・職員の画面を止めるか）、領収書の扱い。短い名前は billing。"

## 背景と解決する困りごと

| ペルソナ | 困りごと | この機能で変わること |
|---|---|---|
| 猪熊さん（施設長） | アプリを導入しても、利用料の申し込みや支払いのたびに書類のやりとりや振込の手間がかかると、導入をためらう | 管理画面からカードで申し込むだけで、毎月の利用料が自動で支払われる。いまの契約の状態もいつでも確かめられる |

この機能は、課題要件の MUST「決済機能を組み込む」を満たすためのもの（Constitution「課題要件（講師指定・必須）」の決済、原則 V）。
家族や介護職員が直接使う機能ではない。最初の申し込みは施設長（猪熊さん）が申し込みページから行い、契約後の確認・変更・解約は施設長と事務員が行う。

## Clarifications

### Session 2026-10-20

- Q: 施設長はどのペルソナか？ → A: 猪熊さん
- Q: 事務員は利用料の画面で何ができるか？ → A: 施設長と同じく、契約の状態を見る・申し込む・カードの変更・解約までできる
- Q: 支払いに失敗したとき・解約したとき、家族や職員はアプリを使えるか？ → A: 今までどおり全員使える。施設長・事務員の管理画面にだけ案内を出す（家族・職員の画面には出さない）
- Q: プランと金額は？ → A: プランは 1 つ、月額 10,000 円（仮）。支払い方法はカードだけ、無料のお試し期間はなし
- Q: 領収書と二重払いはどうするか？ → A: 領収書は決済サービスが用意するものを使う。二重払いは、1 つの申し込み・1 つの施設には同じ支払い画面を使い回して、最初から起きないようにする。それでもすり抜けたときだけ、アプリが 2 つ目の契約を決済サービスで解約し（翌月から請求されないように）、システム管理者が決済サービスの管理画面で返金する
- Q: 毎月の支払いに失敗したとき、施設長・事務員に、管理画面の表示とは別に知らせを送るか？ → A: 決済サービスの標準のメール（支払い失敗のお知らせ）に任せる。アプリは管理画面に表示するだけで、メールやアプリ内のお知らせは送らない
- Q: 解約したあとで、施設長・事務員がもう一度申し込めるようにするか？ → A: できる。解約済みの施設には、管理画面に「申し込む」ボタンを出す
- Q: 契約する前の施設の施設長・事務員のアカウントは、どうやってでき、契約前にアプリを使えるか？ → A: ログインしなくても開ける申し込みページで支払うと、施設と施設長のアカウントができる（自分で申し込む形）。契約前の施設のアカウントはない
- Q: 施設長のアカウントができたあと、施設長はどうやって初めてログインするか？ → A: 申し込みページでパスワードだけを先に決めてもらう。ログイン用の ID は、支払いが確かめられたときにアプリが決まった形で作り、申し込み完了の画面に表示する（ID の形をそろえ、開発前MTG の「職員の ID は付与する」に合わせるため）。メールアドレスは連絡用で、ログインには使わない
- Q: 申し込みページから、2 つ目以降の施設も申し込めるようにするか？ → A: 複数施設に対応するまでの安全のため、2 つ目は受け付けない。今のアプリはデータを施設ごとに分けていないので、2 つ目の施設ができると、ほかの施設の記録が見えてしまうため。すでに施設があるときは、申し込みページは「ページが見つかりません」と表示する（理由は外に出さない）。Constitution の改定は行わない
- Q: 利用料の画面を、使えない役割の人が開いたらどう表示するか？ → A: 職員（介護職員・リーダー・生活相談員）には「この画面を使う権限がありません」と表示する。家族には管理画面の存在を知らせないよう「ページが見つかりません」と表示する。どちらも操作は受け付けない
- Q: ログイン用の ID を、施設長が控えそこねたらどうするか？ → A: 申し込み完了の画面に表示し（「控えてください。同じ内容をメールでもお送りしました」）、同じ ID を書いたメールも連絡用のアドレスに送る（パスワードは書かない。末尾に「心当たりがない場合は、このメールを破棄してください」）。完了画面からログイン画面へ進める。メールは作り込み（Day 4 以降）で足し、ミニマム版は画面の表示だけ（ミニマム版の画面は「控えてください」だけにし、メールの一文はメールを作ってから足す）
- Q: 連絡用のメールアドレスが正しいかを確かめるか？ → A: 2 回入力してもらい、一致を確かめる（打ち間違いを防ぐ）。本人のアドレスかの確認（認証）は今回は行わない。作り込みで余力があれば、パスワードを期限つきのメールのリンクから決める形に変え、メールアドレスの確認も兼ねる
- Q: パスワードはいつ決めるか？ → A: 今は申し込みページで決める（ミニマム版に間に合わせるため）。余力があれば、ID ができたあとに連絡用のアドレスへ送る期限つきのリンクから決める形に変える
- Q: 初期データの施設があると申し込みページが開けない。契約の状態に「未契約」を足し、初期データの施設長が管理画面から申し込む形にするか？（PR #25 のレビュー） → A: 足さない。「入力して申し込む → 支払う → 施設とアカウントができて使い始める」の流れと、「契約前の施設のアカウントはない」の決定を保つため。初期データは、施設がすでにあればその施設に入居者・職員・家族を足す形にし、デモは「空の DB で申し込む → 初期データを入れる → ほかの機能」の順で行う。Day 3 の量は、FR-014（申し込みは同時に 1 つだけ）を作り込みに回して減らす
- Q: 月額の金額は、企画案の月 20,000 円（仮）にそろえるか？（PR #25 のレビュー） → A: そろえない。企画案は検討したときの記録で、金額はこの spec の月額 10,000 円（仮）を正とする

## User Scenarios & Testing *(mandatory)*

> スプリント順にかかわらず、1 週目のうちに最小限の版を動かす（Constitution 原則 V）。
> ミニマム版（Day 3）のゴールは User Story 1（ID を書いたメール（FR-005）と、申し込みを同時に 1 つだけにする仕組み（FR-014）は作り込み）。
> User Story 2 以降は作り込み（Day 4 以降）で扱う。

### User Story 1 - 施設長が申し込みページから申し込み、支払う (Priority: P1)

アプリをまだ使っていない施設の施設長は、ログインしなくても開ける「申し込みページ」で、
施設名・施設長の名前・連絡用のメールアドレス（確認のため 2 回）と、ログイン用のパスワードを入力し、月額の利用プランを申し込む。
決済サービスの支払い画面でカード情報を入力して支払い、支払いが確かめられると、
施設と施設長のアカウントができ、施設の契約状態が「契約中」になる。
ログイン用の ID はアプリが決まった形で作り、申し込み完了の画面に表示し、同じ内容をメールでも送る。施設長は、その ID と申し込みで決めたパスワードで、そのままログインできる。
カード情報はアプリでは受け取らず、決済サービスの画面だけで入力する。

**Why this priority**: 課題要件の MUST。Day 3 の全員での通しのデモ（「Stripe で払う」）に入っている。
これがないと、決済の要件を満たせない。

**Independent Test**: ログインせずに申し込みページを開き、テスト用のカード番号で申し込むと、
施設と施設長のアカウントができ、その施設の契約状態が「契約中」になることを確かめる。実際のお金は動かない。

**Acceptance Scenarios**:

1. **Given** ログインしていない, **When** 申し込みページを開く,
   **Then** プラン名・月額の金額と、施設名・施設長の名前・連絡用のメールアドレス（確認用にもう 1 回）・ログイン用のパスワードの入力欄、「申し込む」ボタンが表示される
2. **Given** 必要な項目を入力して「申し込む」を押した, **When** 決済サービスの支払い画面でテスト用のカード情報を入力して支払う,
   **Then** アプリの申し込み完了の画面に戻り、支払いが確かめられると、施設と施設長のアカウントができ、契約状態が「契約中」になる
   申し込み完了の画面に、アプリが作ったログイン用の ID と「控えてください。同じ内容をメールでもお送りしました」が表示され
   （ミニマム版は「控えてください」だけ。メールの一文は FR-005 のメールを作ってから足す）、
   画面からログイン画面に進んで、その ID と申し込みで決めたパスワードでログインできる
3. **Given** 支払い画面で支払いをやめて戻った, **When** 申し込みページに戻る,
   **Then** 「お申し込みは完了していません」と表示され、施設やアカウントは作られない
4. **Given** 支払いは終わったが、決済サービスからの支払い完了の知らせがまだ届いていない, **When** 申し込み完了の画面に戻る,
   **Then** 「お支払いを確認しています」と表示され、知らせが届いてからアカウントができる
5. **Given** 申し込みページで入力している, **When** メールアドレスを入力する,
   **Then** 2 回入力したメールアドレスが一致しなければ「メールアドレスが一致しません」と表示され、支払い画面には進まない。
   メールアドレスがほかで使われているかどうかは確かめず、表示もしない（連絡用でログインには使わないため。登録の有無が外にわからないようにする）
6. **Given** 解約済みの施設の施設長または事務員がログインしている, **When** 管理画面の「利用料のお支払い」を開く,
   **Then** 「申し込む」ボタンが表示され、ログインしたまま申し込み直せる（新しい施設やアカウントは作られない）
7. **Given** 施設長・事務員以外の役割でログインしている, **When** 「利用料のお支払い」の画面や操作を使おうとする,
   **Then** 操作は受け付けられない。介護職員・リーダー・生活相談員には「この画面を使う権限がありません」、
   家族には「ページが見つかりません」と表示される
8. **Given** すでに「契約中」の施設の施設長または事務員がログインしている, **When** 「利用料のお支払い」を開く,
   **Then** 「申し込む」ボタンは表示されない。古い画面から申し込もうとした場合も受け付けず、「すでにご契約中です」と表示する（二重に申し込めない）
9. **Given** すでに施設が 1 つ登録されている（契約の状態は問わない）, **When** ログインしていない人が申し込みページを開く,
   **Then** 「ページが見つかりません」と表示され、申し込みはできない（複数施設に対応するまでの安全のため。理由は表示しない）
10. **Given** アカウントができた, **When** 連絡用のメールアドレスを確かめる,
    **Then** ログイン用の ID（パスワードは書かない）と、末尾に「心当たりがない場合は、このメールを破棄してください」と書いたメールが届いている（作り込みで追加。ミニマム版は画面の表示だけ）

### User Story 2 - 施設長・事務員が契約の状態と請求の予定を確かめる (Priority: P2)

施設長と事務員は、管理画面で、いまの契約の状態（契約中／支払いに失敗／解約予定／解約済み）と、
月額の金額、次の請求日を確かめられる。

**Why this priority**: 支払いが自動で続く仕組みでは、「いま払えているか」「次はいつ引き落とされるか」が
分からないと施設が不安になる。US1 のあとに、同じ管理画面に足すだけで作れる。

**Independent Test**: 契約中の状態と、支払いに失敗した状態の施設を用意し、
施設長・事務員でログインして、状態と次の請求日が正しく表示されることを確かめる。

**Acceptance Scenarios**:

1. **Given** 契約中の施設, **When** 施設長または事務員が「利用料のお支払い」を開く,
   **Then** 「契約中」・プラン名・月額の金額・次の請求日が表示される
2. **Given** 決済サービスで毎月の支払いに失敗した, **When** 施設長または事務員が「利用料のお支払い」を開く,
   **Then** 「お支払いに失敗しました」と、カードを確かめるよう案内が表示される
3. **Given** 契約状態が「支払いに失敗」または「解約済み」, **When** 家族や介護職員がアプリを開く,
   **Then** 今までどおり使え、利用料についての案内は表示されない（FR-017。解約済みで利用を止めるのは今後の実装。[Assumptions](#assumptions) を参照）

### User Story 3 - 施設長・事務員がカードの変更・解約・請求の履歴を扱う (Priority: P3)

施設長と事務員は、管理画面から決済サービスの管理画面に移り、支払いに使うカードの変更、
解約、過去の請求と領収書の確認ができる。

**Why this priority**: 契約が続く以上、カードの期限切れや解約は必ず起きる。ただし、決済の要件は US1 で満たせるので、
作り込みとして扱う。

**Independent Test**: 契約中の施設の施設長（または事務員）で決済サービスの管理画面に移り、テスト用の別のカードに変える・解約する・
請求の履歴を見る、がそれぞれでき、アプリの契約状態に反映されることを確かめる。

**Acceptance Scenarios**:

1. **Given** 契約中の施設の施設長または事務員, **When** 「カードの変更・解約・請求の履歴」を押す,
   **Then** 決済サービスの管理画面が開き、その施設の契約だけが表示される
2. **Given** 決済サービスの管理画面で解約した, **When** アプリの管理画面に戻る,
   **Then** 契約状態が「解約予定」になり、いつまで使えるかが表示される
3. **Given** 決済サービスの管理画面, **When** 施設長または事務員が過去の請求を開く,
   **Then** 請求ごとの金額と領収書を確かめられる

### Edge Cases

- 決済サービスからの知らせ（支払い完了・失敗・解約など）が、同じ内容で 2 回以上届いた場合
  → 2 回目以降は何も変えない（契約状態が二重に変わったり、記録が重複したりしない）。
- 決済サービスからの知らせが、届く順番を入れ替えて届いた場合（例：「解約」のあとに古い「支払い完了」）
  → 決済サービス上の最新の状態に合わせ、古い知らせで状態を戻さない（FR-012）。
- 決済サービスを名乗る、偽の知らせが届いた場合 → 送り主を確かめられない知らせは受け付けず、契約状態を変えない。
- 支払い画面の途中でブラウザを閉じた場合 → 支払いが終わっていなければ、施設もアカウントも作られない。終わっていれば、知らせが届いた時点でアカウントができ「契約中」になる。
- 申し込みページで入力したが、支払わずに終わった申し込み → 施設やアカウントは作らない。入力された情報は、支払われないまま一定時間たったら消す。
- 同じ人が「申し込む」を二度押ししたり、2 つのタブで開いたりした場合 → 同じ申し込みには同じ支払い画面を使い回し、
  支払い画面では 1 回しか払えないので、二重には払えない（FR-013）。
- 解約済みの施設で、施設長と事務員が同時に「利用料のお支払い」を開き、それぞれ「申し込む」を押した場合 → どちらも止めず、
  2 人とも同じ支払い画面に進む。先に払ったほうで「契約中」になり、二重には払えない（FR-013）。
- 知らない 2 人が申し込みページからほぼ同時に申し込もうとした場合 → 支払いが終わっていない申し込みは同時に 1 つだけにして防ぐ（FR-014。作り込み）。
  支払い画面には有効期限を付け、期限が切れたら次の人が申し込める。それでもタイミングが重なってすり抜け、両方の支払いが終わったときだけ、
  施設は先に確かめられた 1 つだけ作り（FR-016）、もう一方は、アプリが決済サービスで契約を解約し（翌月から請求されないように）、
  支払いはシステム管理者が決済サービスの管理画面で返金する（アプリに返金の機能は作らない）。
- 支払いが済んだのに、対応する申し込みが見つからない場合（「戻る」で取り消した直後に別のタブで払い終えた、など）
  → アカウントは作れない（パスワードがない）ので、アプリが決済サービスでその契約を解約し（翌月から請求されないように）、
  ログに残す。返金はシステム管理者が行う（FR-016 と同じ）。
- 誰かが申し込みページから何度も申し込んだり、支払い画面を開いたまま放置したりして、本物の施設長が申し込めなくなる場合
  → 短い時間に同じところから何度も申し込まれたら止める（FR-027。作り込み）。放置された申し込みは、支払い画面の有効期限で消える（FR-014）。
- 支払いに失敗したり、解約したりした場合の、家族・職員のアプリの使い方 → 今までどおり全員使える（FR-017）。
- 毎月の支払いに失敗した場合の、施設長・事務員への知らせ → アプリからは送らない。決済サービスの標準のメールに任せ、アプリは管理画面に表示するだけ（FR-021）。

## Requirements *(mandatory)*

### Functional Requirements

**申し込みと支払い（US1）**

- **FR-001**: System MUST ログインしていない人が申し込みページから、施設名・施設長の名前・連絡用のメールアドレス・ログイン用のパスワードを入力して、
  月額の利用プランを申し込めるようにする。解約済みの施設は、施設長・事務員がログインしたまま管理画面から申し込み直せる。
- **FR-002**: System MUST 施設と施設長のアカウントは、決済サービスから支払い完了の知らせを受け取り、確かめたあとにだけ作る。
  支払いが終わっていない申し込みでは、施設もアカウントも作らない。
- **FR-003**: System MUST 施設長のログイン用の ID は、支払いが確かめられたときにアプリが決まった形で作り、申し込み完了の画面に表示する。
  申し込む人に ID を決めさせない。メールアドレスは連絡用で、ログインには使わず、ほかで使われているかの確認もしない。
- **FR-004**: System MUST 連絡用のメールアドレスを 2 回入力させ、一致しないときは支払い画面に進ませない。
- **FR-005**: System MUST アカウントができたら、連絡用のメールアドレスに、ログイン用の ID を書いたメールを送る。パスワードは書かない。
  末尾に「心当たりがない場合は、このメールを破棄してください」と書く。同じアカウントには 1 通だけ送る（同じ知らせが何回届いても増やさない）。
  ミニマム版（Day 3）では作らない（画面の表示だけ）。
- **FR-006**: System MUST 申し込みページで入力されたパスワードは、元に戻せない形（ハッシュ）でだけ保存し、画面・ログ・決済サービスに渡さない。
  支払われないまま一定時間たった申し込みは、パスワードを含めて消す。
- **FR-007**: System MUST 利用料の画面（契約の状態）と、申し込み・カードの変更・解約の操作を、施設長と事務員の役割にだけ許可する。
  家族・介護職員・リーダー・生活相談員には、画面も操作も使わせない（Constitution「利用者と権限」）。
  介護職員・リーダー・生活相談員には権限がないことを伝え、家族には画面があること自体を知らせない（「ページが見つかりません」）。
- **FR-008**: System MUST カード番号などのカード情報を、アプリの画面・サーバー・データベース・ログのどこでも受け取らず、
  保存しない。カード情報の入力は、決済サービスが用意する支払い画面だけで行う。
- **FR-009**: System MUST 施設の契約状態を、決済サービスからの知らせ（支払い完了・支払い失敗・解約など）にもとづいて更新する。
  支払い画面から戻ってきたことだけを根拠に「契約中」にしない。
- **FR-010**: System MUST 決済サービスからの知らせは、送り主が決済サービスであることを確かめてから受け付ける。
  確かめられない知らせは受け付けず、記録に残す。
- **FR-011**: System MUST 同じ知らせが繰り返し届いても、結果が 1 回分と同じになるようにする。
- **FR-012**: System MUST 決済サービスからの知らせが届く順番が入れ替わっても、決済サービス上の最新の状態に合わせ、古い知らせで契約状態を戻さない。
- **FR-013**: System MUST 同じ申し込みで「申し込む」を何度押しても（二度押し・戻って押し直しなど）、申し込みと支払い画面は 1 つだけにする。
  申し込み直し（解約済みの施設）では、施設長・事務員の誰が何度押しても、その施設に開いている同じ支払い画面に案内する。
  どの施設かは、ログインしている人が所属する施設で見分け、施設名では見分けない。
  アプリの「利用料のお支払い」の画面は、何人が同時に開いてもよい。
- **FR-014**: System MUST 申し込みページで、支払いが終わっていない申し込みは同時に 1 つだけにする
  （申し込みページではまだ施設がなく、同じ施設の申し込みかを見分けられないため）。支払い画面には有効期限を付け、
  期限が切れた申し込みは消して、次の申し込みを受け付ける。ミニマム版（Day 3）では作らない（デモでは起きないため。作り込みで足す）。
- **FR-015**: System MUST 施設が 1 つにつき、同時に有効な契約は 1 つまでにする。
- **FR-016**: System MUST 複数施設に対応するまでの安全のため、施設が 1 つ登録されたあとは、申し込みページからの新しい申し込みを受け付けない
  （申し込みページは「ページが見つかりません」と表示し、理由は出さない）。
  2 つの申し込みの支払いがほぼ同時に確かめられた場合も、施設は 1 つしか作らず、もう一方の契約は決済サービスで解約する。

**契約状態とアプリの利用（US2・US3）**

- **FR-017**: System MUST 契約状態が「支払いに失敗」「解約済み」になっても、家族・職員を含む全員が今までどおりアプリを使えるようにする。
  利用料についての案内は、施設長と事務員の管理画面にだけ表示し、家族・職員の画面には表示しない。
- **FR-018**: System MUST 管理画面に、施設の契約状態（契約中／支払いに失敗／解約予定／解約済み）、プラン名、
  月額の金額、次の請求日を表示する。
- **FR-019**: System MUST 契約状態が変わったとき、いつ・どの状態からどの状態に変わったかを記録する。
- **FR-020**: System MUST 施設長と事務員が、カードの変更・解約・過去の請求と領収書の確認を行えるようにする（US3）。
  ミニマム版（Day 3）では作らない。
- **FR-021**: System MUST 支払いの失敗を、アプリからはメール・アプリ内のお知らせで知らせない（管理画面の表示だけ）。
  施設長・事務員への支払い失敗のメールは、決済サービスの標準の機能（設定でオンにする）に任せる。

**安全性・ログ（課題要件より）**

- **FR-022**: System MUST 決済サービスとつなぐための秘密の情報（鍵など）を、コードやリポジトリに含めない。
- **FR-023**: System MUST 開発と本番でログの詳しさを分け、どちらのログにもカード情報・秘密の情報を出さない。
- **FR-024**: System MUST 開発・デモは決済サービスのテスト用の環境だけを使い、実際の請求を発生させない。
- **FR-025**: System MUST 決済サービスには、施設名・連絡用のメールアドレスなど、支払いに必要な情報だけを渡す。
  入居者・家族・連絡帳などの情報は渡さない（万一どこかから漏れたときの被害を小さくするため）。
- **FR-026**: System SHOULD 決済サービスとつなぐ鍵は、このアプリに必要な操作だけができるものを使う。
  鍵が漏れたときに、新しい鍵に差し替えて古い鍵を使えなくする手順を決めておく。作り込みで余力があれば行う。
- **FR-027**: System MUST ログインなしで開ける申し込みページの書き込みにも、ほかの書き込みと同じなりすましの対策（spec 001 の research.md R-03）を当てる。
  また、短い時間に同じところから何度も申し込まれたら止める（ログインの試行回数の制限と同じ考え方。作り込み）。

### Key Entities *(include if feature involves data)*

- **施設**: アプリを導入している施設（1 つの前提）。決済サービス上の顧客と 1 対 1 で結びつく。
- **契約（利用プランの申し込み）**: 施設とプランの組み合わせ。状態（契約中／支払いに失敗／解約予定／解約済み）、
  月額の金額、次の請求日、解約日。施設ごとに有効なものは 1 つまで。
- **プラン**: 月額の利用プラン。名前と月額の金額を持つ。
- **決済サービスからの知らせ**: 支払い完了・失敗・解約などの知らせ。同じ知らせを二重に処理しないために、受け付けたものを記録する。
- **契約状態の変更履歴**: いつ・どの状態からどの状態に変わったか。
- **申し込み**: 申し込みページで入力された施設名・施設長の名前・連絡用のメールアドレス・パスワード（元に戻せない形）と、支払いの状態。支払いが確かめられたら、施設と施設長のアカウントになる。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 施設長が申し込みページを開いてから、入力・テスト用カードでの支払いを終えて、完了画面に表示された ID と申し込みで決めたパスワードでログインできるまで、5 分以内に終わる。
- **SC-002**: 支払いを終えてから 1 分以内に、施設のアカウントができ、契約状態が「契約中」になる。
- **SC-003**: 同じ支払い完了の知らせを 3 回続けて送っても、施設・施設長のアカウント・契約はそれぞれ 1 つで、状態の変更履歴も 1 件だけ増え、ID を書いたメールも 1 通だけ送られる（テストシナリオで確認）。
- **SC-004**: 送り主を確かめられない知らせを送っても、契約状態は 1 度も変わらない（テストシナリオで確認）。
- **SC-005**: アプリの画面・データベース・ログのどこにも、カード番号が 1 件も残っていない（テストシナリオで確認）。
- **SC-006**: 施設長・事務員以外の役割では、「利用料のお支払い」の画面・操作に 1 回もたどり着けない（役割ごとのテストで確認）。
- **SC-007**: パスワードが、データベース・ログ・決済サービスのどこにも、元の文字のまま 1 件も残っていない（テストシナリオで確認）。
- **SC-008**: 「解約」の知らせのあとに古い「支払い完了」の知らせを送っても、契約状態は「解約」のまま戻らない（テストシナリオで確認）。
- **SC-009**: 申し込みページで「申し込む」を素早く 2 回押しても、申し込みと支払い画面は 1 つだけできる（テストシナリオで確認）。
- **SC-010**: 決済サービスの管理画面で施設の顧客情報を開いても、入居者・家族・連絡帳の情報が 1 件も載っていない（テストシナリオで確認）。

## Assumptions

- 施設は 1 つ（Constitution「施設の前提」）。今のアプリはデータを施設ごとに分けないため、複数施設に対応するまでの安全のため、申し込みページから申し込めるのは最初の 1 施設だけにする。
  サービスとして全国の施設に広げること（施設ごとにデータを分ける、申し込んだ施設が実在するかの審査・承認など）は、この 10 日間の範囲外。
  本番では、申し込みのあとに施設の審査（承認）を入れる想定。
- 開発用の初期データ（spec 001 の T015）は、施設がまだなければ施設を「契約中」として作り、すでにあればその施設に入居者・職員・家族を足す。
  普段の開発は初期データだけで進め（申し込みページは閉じている）、申し込みを確かめるときとデモは、空の DB から「申し込む → 初期データを入れる」の順で行う。
  初期データで作った施設は決済サービスとつながっていないので、次の請求日の表示やカードの変更（US2・US3）は、申し込みで作った施設で確かめる。
- プランは 1 つだけ。金額は仮に月額 10,000 円とし、テスト用の環境なので実際には請求されない。
  プランを増やすことはこの spec では扱わない。
- 支払い方法はクレジットカードだけ。請求書払い・口座振替は扱わない。
- 無料のお試し期間は設けない。
- 支払いに失敗したときの再請求（いつ・何回やり直すか）は、決済サービスの標準の動きに任せる。
- 本番では、解約済みの施設の家族・職員はアプリを使えないようにする（施設長・事務員は「利用料のお支払い」だけ使え、申し込み直せる）。
  この 10 日間では作らず、今後の実装とする（FR-017 のとおり全員使える）。止める確認はログインの共通の仕組み 1 か所で足せるので、
  作り込みで余力があれば足す。解約済みでも記録は消さない。デモでは解約済みの状態は見せない。
- 領収書は、決済サービスが用意するものを使う（アプリで領収書を作らない）。テスト用の環境では領収書のメールは自動で送られないため、
  デモでは請求の履歴の画面（US3）で確かめる。
- 支払い失敗のお知らせなど、決済サービスが契約者に送るメールは、テスト用の環境では基本的に送られない
  （契約者のメールアドレスが、決済サービスのアカウントのチームメンバーのものなどの場合だけ送られる）。デモでは見せなくてよい。
- カードの変更・解約・請求の履歴（US3）は、決済サービスが用意する管理画面を使い、アプリでは同じ画面を作らない。
- 契約の金額や状態をシステム管理者（アプリ会社）が見る画面は、この spec では扱わない（決済サービスの管理画面で確かめる）。
- ログインと役割は、基盤（ようこ担当）で作る仕組みを使う。施設長・事務員は一人ずつ ID でログインする（開発前MTG の決定）。
  施設長の ID の決まった形（例：施設番号＋連番）は plan で決め、職員の ID と同じ形にそろえる。
- パスワードの決まり（長さ・使える文字など）は、ログイン全体で共通の決まり（基盤で決める）に従う。
- 連絡用のメールアドレスが本人のものかの確認（認証）は行わない。2 回入力で打ち間違いだけを防ぐ。
  作り込みで余力があれば、パスワードを申し込みページで決める今の形をやめ、連絡用のアドレスに送る期限つきのリンクから
  パスワードを決める形に変える（メールアドレスが本人のものかも同時に確かめられる）。本番では審査（承認）のときにも確かめる。
- ID を書いたメールは、家族の招待・通知と同じメール送信の仕組みを使う（開発・デモは Mailpit で確かめる）。
- 事務員やほかの職員のアカウントは、契約後に施設長が作る（基盤のアカウント管理）。申し込みページで作るのは施設長のアカウントだけ。
- アプリ側の画面（「利用料のお支払い」）は、Constitution の UI 方針（固定の文言の漢字にふりがな、多言語の切り替え）に従う。
  決済サービスが用意する支払い画面・管理画面は対象外。ミニマム版では日本語だけでよい（作業分担MTG のミニマム版ルール）。
- 実在の施設やカード情報は使わない。デモは架空の施設とテスト用のカード番号だけを使う（Constitution「個人情報」）。
