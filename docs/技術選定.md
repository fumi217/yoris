# 技術選定

> **ステータス**: 提案（未決定）。チームの会議で案1〜3から決め、決定後に「2. 技術スタック一覧」の
> 採用技術欄を確定させる。決定の経緯は議事録（`docs/context/meeting/`）に残す。

## 1. 選定方針

優先する順に並べる。

1. **課題要件を満たせること**（下表）。
2. **チームが理解しながら作れること**。スプリントレビューの Try「スケジュールに追われるよりも理解を優先」
   と、講師コメント「フレームワークの違いや、作るアプリに合わせたものを調べてみて決める」に合わせる。
   経験に差があるため、担当をまたいで助け合える（読める・直せる）ことを重視する。
3. **2 週間（SEC10・11）で動くものを出せること**。設定や運用に時間がかかる技術は避ける。
4. **このアプリに合っていること**。家族はスマートフォン、職員は施設のタブレットで使う。
   画面は日本語・インドネシア語・英語を切り替える。AI は医療判断をせず、
   施設が家族に開示した記録だけを根拠に答える。

### 課題要件との対応

| 要件 | 区分 | 対応する技術（全案共通） |
| --- | --- | --- |
| Web アプリ、フロントとバックを分離 | MUST | `frontend/` と `backend/` を別アプリにし、API で通信 |
| AI Agent の技術要素 | MUST | Claude API のツール呼び出し（問い合わせ AI エージェント） |
| コンテナ利用 | MUST | Docker / Docker Compose（開発）、コンテナのまま本番デプロイ |
| キャッシュサーバー | MUST | Redis |
| 決済機能 | MUST | Stripe Billing（テストモード）。施設がアプリ会社に払う月額利用料 |
| XSS・SQL インジェクション対策 | MUST | 表示時の自動エスケープ（React）、ORM によるパラメータ化 |
| 単体テストのテストコード | MUST | 各案のテストフレームワーク（下表） |
| 開発と本番のログの出し分け | MUST | 構造化ログのライブラリを環境変数で切り替え |
| 本番デプロイ・サブドメイン・https | ADVANCE | Render ＋ 独自ドメイン（`app.` / `api.` サブドメイン、証明書は自動） |
| フロントのテスト自動化 | ADVANCE | Playwright を GitHub Actions で実行 |
| プロンプトインジェクション対策 | ADVANCE | AI のツール側で、ログイン中の家族に開示された記録しか返さない |

## 2. 技術スタック一覧

### 全案で共通にするもの

| レイヤ | 採用技術 | 候補 | 選定理由 |
| --- | --- | --- | --- |
| データベース | PostgreSQL | MySQL | 記録・開示設定・変更履歴など関連の多いデータを扱う。Render で管理型が使える |
| キャッシュ | Redis | Memcached | ①ログインセッション ②家族ごとの日報の組み立て結果 ③AI 問い合わせの回数制限、の 3 用途に使える。Memcached はセッションの永続化や回数制限に向かない |
| 認証 | バックエンドが発行するセッション（Cookie、Redis に保存） | Auth0、Firebase Auth | 家族・介護職員・リーダー・相談員・施設長など役割が多く、権限を自前の DB で管理したい。外部サービスの設定を覚える時間も省ける |
| AI | Claude API（ツール呼び出し） | OpenAI API | ツールを「開示された記録を取得する」「相談員に回す」に限定でき、記録にないことは答えない設計にしやすい |
| 決済 | Stripe Billing（テストモード） | PAY.JP | 月額課金・Checkout・顧客ポータル・Webhook がそろっている。情報量が多い |
| コンテナ | Docker / Docker Compose | — | 開発は frontend・backend・PostgreSQL・Redis を一括起動 |
| ホスティング | Render | Fly.io、Google Cloud Run、AWS（ECS） | コンテナのままデプロイでき、独自ドメインの https 化が自動、PostgreSQL と Redis も同じ場所で用意できる。AWS は学びが多いが 2 週間ではインフラ担当の負担が大きい |
| ドメイン | 独自ドメインを 1 つ取得し、`app.` と `api.` のサブドメインを割り当てる | — | ADVANCE 要件（サブドメイン・https） |
| CI / CD | GitHub Actions（lint・単体テスト・E2E）、Render の自動デプロイ | — | リポジトリと同じ場所で完結する |
| 通知（スプリント 3） | Web Push（PWA） | ネイティブアプリ | アプリストアに出さずにスマートフォンへ通知できる |

### 案ごとに変わるもの

| レイヤ | 案1: TypeScript 統一（推奨） | 案2: Python ＋ React | 案3: Rails ＋ Next.js |
| --- | --- | --- | --- |
| フロントエンド | Next.js（React）、Tailwind CSS、next-intl、TanStack Query | React（Vite）、Tailwind CSS、react-i18next、TanStack Query | 案1と同じ |
| バックエンド | Hono（または NestJS）、Prisma、Zod | FastAPI、SQLAlchemy、Pydantic | Ruby on Rails（API モード）、Active Record |
| AI の SDK | Anthropic TypeScript SDK | Anthropic Python SDK | Anthropic Ruby SDK |
| 監視・ログ | pino（開発: 読みやすい形式／本番: JSON、個人情報を伏せる） | structlog | Rails の環境別設定 ＋ lograge |
| 単体テスト | Vitest | pytest（バック）、Vitest（フロント） | RSpec（バック）、Vitest（フロント） |
| E2E・フロント自動テスト | Playwright | Playwright | Playwright |
| 言語の数 | 1（TypeScript） | 2（Python・TypeScript） | 2（Ruby・TypeScript） |

## 3. 比較サマリ

| 観点 | 案1: TypeScript 統一 | 案2: Python ＋ React | 案3: Rails ＋ Next.js |
| --- | --- | --- | --- |
| 助け合いやすさ | ◎ 全員が同じ言語でフロント・バック両方を読める | △ 言語が 2 つ | △ 言語が 2 つ |
| 型・入力チェックの共有 | ◎ Zod の定義をフロントとバックで共有 | ○ OpenAPI から TS の型を自動生成する工程が必要 | △ 共有しにくい |
| AI Agent（F）の作りやすさ | ○ | ◎ 情報・サンプルが最も多い | △ 事例が少ない |
| 登録・編集画面（C・B・G）の速さ | ○ | ○ | ◎ |
| API 仕様書の作りやすさ | ○ | ◎ FastAPI が OpenAPI を自動生成 | ○ |
| 分離の分かりやすさ | ○ Next.js のサーバー機能に業務処理を書かないルールが必要 | ◎ Vite の React はフロント専用 | ○ 案1と同じ注意 |

### 選び方

| チームの状況 | 選ぶ案 |
| --- | --- |
| 講座で JavaScript / TypeScript を学んだ、または経験者が多い | **案1** |
| Python の経験者がいて、AI（F）を見せ場にしたい | 案2 |
| Rails の経験者が 2 人以上いる | 案3 |

迷う場合は**案1**を推奨する。2 週間の短期開発で経験に差があるチームでは、
1 つの言語で全員が全体を読めることが最も効くため。

## 4. リスクと対応

| リスク | 対象 | 対応 |
| --- | --- | --- |
| Next.js のサーバー機能に業務処理を書き、フロントとバックの分離があいまいになる | 案1・案3 | 業務処理・DB アクセスはバックエンドだけに置くことをコーディング規約に明記し、レビューで確認する |
| 言語が 2 つになり、担当外のコードを読めない | 案2・案3 | 型は OpenAPI から自動生成。ペアでレビューする |
| AI が非開示の記録や推測で答える、プロンプトインジェクションで他人の記録を引き出す | 全案 | 入居者 ID と開示範囲はサーバーがログイン情報から決め、AI のツールはその範囲の記録しか返さない。医療的な質問は定型文で相談員につなぐ |
| 開示設定を変えたのに、キャッシュに残った古い日報で非開示項目が表示される | 全案 | 記録・開示設定の更新時に、該当する入居者の日報キャッシュを削除する |
| Stripe の Webhook がローカルで受け取れず、決済の確認が遅れる | 全案 | Stripe CLI で Webhook をローカルに転送して開発する。実課金はしない |
| 本番デプロイ・https・ドメイン設定を後回しにして最終週に詰まる | 全案 | スプリント 1 から、最小構成（Hello World）を本番にデプロイしておく |
| Render の無料枠はスリープや制限があり、発表時に遅い | 全案 | 発表前に有料プランへの切り替えか、事前アクセスで起こしておく |
| 新しい技術の理解が追いつかない | 全案 | 採用ライブラリは表にあるものに限定し、追加するときはチームに共有して理由をこの文書に追記する |
