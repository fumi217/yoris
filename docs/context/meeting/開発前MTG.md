## 1. 記録のデータの形（ゆう）

### 記録を 1 つのテーブルにまとめる

```
care_records（連絡帳の記録）
- id
- resident_id    入居者
- date           日付（眠りは、記録した朝の日付）
- item           項目：meal（食事量）／mood（機嫌・様子）／sleep（眠り）
- slot           区分：breakfast／lunch／dinner／snack（食事）、day（機嫌・眠り）
- value          値（下の表）
- recorded_by    記録した職員
- recorded_at    記録した時刻
- deleted_at     当日中に取り消したら入れる

一意の決まり：「入居者×日付×項目×区分」は、取り消していない記録の中で 1 つだけ（部分インデックス）
```

- `slot` を空にしないのは、PostgreSQL の一意制約では空どうしが別物として扱われ、同じ日の機嫌が 2 つ入ってしまうため（ようこ）。
- 一意の決まりを「取り消していない記録だけ」にするのは、取り消したあとに記録し直せるようにするため（ようこ・みさき）。

| item | value |
|---|---|
| meal | `10`（全部）／`8`（ほぼ全部）／`5`（半分）／`2`（少し）／`0`（食べていない）／`none`（食事なし） |
| mood | `smile`（笑顔が多い）／`normal`（いつもどおり）／`low`（元気がない） |
| sleep | `good`（よく眠れた）／`normal`（いつもどおり）／`poor`（あまり眠れなかった） |

- `item` と `value` は日本語ではなくコードで持つ。画面の文言は、多言語の辞書（react-i18next）でコードから引く（みさき）。
- 修正の履歴は `care_record_histories`（前の値、新しい値、変えた職員、時刻）に残す（spec 001 FR-005）。

## 2. 家族に見せるための共通の関数（ゆう）

**家族に出すもの（連絡帳・AI の F・通知のまとめ）は、必ず次の関数を通す。職員向けのもの（E の変化の検知など）は、非開示の項目も含めて直接読んでよい。**
非開示の項目が家族や AI に漏れない（Constitution 原則 IV）ことを、1 か所で守るため。

| 関数 | 返すもの | 使う人 |
|---|---|---|
| `get_disclosed_records(resident_id, date_from, date_to, items=None)` | 開示済みの記録（id・日付・項目・区分・値・記録した時刻）。`items` で項目を絞れる | さとこ（連絡帳・20 時のまとめ）、みさき（F） |
| `get_disclosed_themes()` | 開示済みの「知りたいこと」のテーマ | さとこ（テーマのボタン） |
| `get_active_replies(resident_id, date_from, date_to)` | 有効な返事（取り消していないもの） | さとこ（連絡帳）、みさき（F、読む場合） |

- 期間で取れるのは、家族が「最近ちゃんと食べてる？」のように 1 日以外のことも聞くため（みさき。AI 側で最大 7 日などに制限する）。
- 記録の id を返すのは、AI の回答がどの記録にもとづくかを追跡するため（Constitution 原則 III、みさき）。
- 記録した時刻を返すのは、20 時のまとめで「その日に新しい記録があるか」を見るため（さとこ）。

## 3. リクエストと返事のデータの形（さとこ・ゆう）

```
requests（家族の「知りたいこと」）… さとこが作る
- id
- resident_id    入居者（家族アカウントは入居者に 1 つなので、家族はここから分かる）
- theme_id       テーマ
- status         waiting（返事待ち）／answered（返事あり）／cancelled（取り消し）
- created_at     送った日時

replies（職員の返事）… ゆうが作る
- id
- request_id     どのリクエストへの返事か
- template_ids   選んだ定型文（1 つ以上）
- note           書き足した短い文（100 文字まで、なくてもよい）
- replied_by     返事をした職員
- replied_at     返事をした時刻
- edited_at      当日中に直した時刻
- read_at        家族が読んだ時刻（家族で共有）
- cancelled_at   当日中に取り消したら入れる
```

### 状態の動き

```
返事待ち ──職員が返事──→ 返事あり ──職員が当日中に取り消し──→ 返事待ち
   │
   └──家族が取り消し──→ 取り消し
```

### ルール

- 返事待ちは 1 家族 3 件まで、同じテーマは 1 件まで（FR-014）。DB の決まり（返事待ちだけを対象にした部分インデックス）とアプリ側の確認の両方で守る（さとこ）
- 最初に保存された返事だけを有効にする（FR-030）：返事を保存するときに「状態が返事待ちなら返事ありにする」を 1 回の更新で行い、
  更新できなかったら、ほかの職員が先に返事したか、家族が取り消したと判断する
- 返事を直したら `edited_at` を残し、未読には戻さない（再通知しないため、さとこ）
- 返事の保存を確定したあとに、さとこの `create_reply_notice(reply_id)` を呼ぶ。取り消し・修正のときは呼ばない。
  通知の作成に失敗しても、返事の保存は取り消さない

| 作る人 | API | 中身 |
|---|---|---|
| さとこ | `GET /api/family/contact-book` | 家族の連絡帳 |
| さとこ | `GET /api/family/themes` | テーマ一覧（`get_disclosed_themes` を通す） |
| さとこ | `GET /api/family/requests` | 家族が送ったリクエストの一覧 |

| ゆう | `POST /api/staff/requests/{id}/reply` | 職員が返事する |

## 4. DB の土台・ログイン（ようこ）

- ようこが、Day 1 の午前に、全員が使うテーブルを作る
  - 施設（`facilities`）：Stripe の契約状態・顧客 ID と、開示設定の置き場所
  - ログイン用の `users`（職員は ID、家族はメールアドレスでログイン。パスワード・役割）
  - 入居者（`residents`）、職員（`staff`）、家族アカウント（`family_accounts`）。職員と家族は `users` につなぐ
- 「ログイン中の人」の形を、仮のログインの時点で決める。各自の API はこれを受け取る：
  利用者 ID、職員か家族か、役割、家族なら入居者 ID。Day 2 に本物のログインに差し替えても、各自のコードを直さずに済む
- 仮のログイン：開発環境だけで使える「ユーザー切り替え」。環境変数で本番では止め、止まっていることをテストで確かめる
- それ以外のテーブルは、各自が自分の機能の PR の中で追加する
  - さとこ：`requests`、`notifications`（お知らせの履歴）、`notification_settings`（通知設定）、献立表のファイル
  - みさき：`inquiries`（問い合わせの履歴と、使った記録の id）、`escalations`（相談員に回したもの）
  - ゆう：`care_records`、`care_record_histories`、`replies`、開示設定、テーマ・定型文
- マイグレーションは、作る直前に main を取り込む。ぶつかったら、後からマージする人が直す
- OpenRouter のキーとモデル名の環境変数を、Docker Compose に足す（みさき → ようこ）
- 施設のタブレットを使い回すので、交代のときのログアウト忘れに注意する（作り込みで、一定時間で自動ログアウトなどを検討）
