# テスト設計書

## 1. テスト方針

- 目的・品質ゴール
- カバレッジ目標（例：ライン 80% 以上）
- テストピラミッドの考え方（単体 > 結合 > E2E）

## 2. テスト種別と範囲

| 種別           | 対象                          | ツール                   | 担当       |
| -------------- | ----------------------------- | ------------------------ | ---------- |
| 単体テスト     | 関数・コンポーネント単位      | Jest / Vitest            |            |
| 結合テスト     | API ・モジュール間            | Supertest 等             |            |
| E2E テスト     | ユーザー操作のシナリオ        | Playwright / Cypress     |            |
| 性能テスト     | 想定負荷でのレイテンシ        | k6 / JMeter              |            |
| セキュリティ   | 認証・認可・OWASP Top 10      | OWASP ZAP 等             |            |

## 3. テストケース管理

- 管理場所（リポジトリ / スプレッドシート / TestRail 等）
- ID 採番ルール
- 不具合のチケット化フロー

## 4. テスト環境

- 開発 / ステージング / 本番の差分
- テストデータ作成方針

## 5. 受け入れ基準（Definition of Done）

- 全テストが green
- カバレッジ基準を満たす
- セキュリティスキャンで重大な指摘がない

## 6. 結合・総合テストのシナリオと結果

機能（spec）ごとに、quickstart.md の確認の流れをシナリオにして、確かめ方と結果を書く（Constitution の課題要件。001-T093）。
確かめ方は、**E2E**（Playwright。`docker compose --profile e2e run --rm e2e`）、**pytest**（backend の自動テスト。CI で毎回動く）、**手動**（ブラウザで動かして見る）のどれか。
