# PRD

> 各機能の詳しい仕様は `specs/<機能>/spec.md` が正（Constitution「記録のルール」）。この PRD は全体像をまとめ、spec と食い違わないようにそろえる。

### 1. プロジェクト概要（Overview）

- プロダクト名：家族連絡アプリ（仮）
- 作成日：2026-10-21
- 一言でいうと：介護施設に入居している家族の日々の様子を、施設に電話も遠慮もせずに知れる、施設と家族の連絡帳アプリ。
  職員の入力はボタン中心で、家族の「知りたいこと」への返事や問い合わせへの一次対応で、職員の負担を増やさない
- チーム：さとこ（リーダー）・みさき・ゆう・ようこ（[README の体制](../README.md#体制)）

---

### 2. 背景（Background）

#### なぜこのプロダクトが必要か

- 介護施設に家族を預けている人は、**日々の様子が分からず不安**を抱えている。ただ、忙しそうな施設に「今日はどうでしたか？」と電話するのは**気が引ける**。
  仕事をしている家族は、電話できるのが昼休みなどに限られる
- 施設の職員は、お世話（ケア）の最中に家族からの電話で呼ばれ、**業務が中断**される。家族対応の窓口になる生活相談員には、問い合わせが集中する
- 外国人の介護職員が増えており、**日本語で記録を書く負担**が大きい。家族と話す機会もない。
  介護分野の特定技能外国人は、2026 年 6 月末で **79,884 人**（速報値。特定技能全体の 18.0%）で、半年前（2025 年 12 月末）の 67,871 人から増えている
  （出典：[出入国在留管理庁「特定技能制度運用状況」](https://www.moj.go.jp/isa/content/001428398.pdf)）
- 介護施設への入居に関わった人への民間の調査では、**66.6%** が「入居後、家族・親族の普段の様子が分からず不安を感じたことがある」と答えている
  （「とてもある」17.3%・「ややある」49.3%。2026 年 7 月、インターネット調査、300 人。
  出典：[株式会社元気な介護・未知株式会社「家族への情報共有に関する実態調査」（PR TIMES、2026-07-31）](https://prtimes.jp/main/html/rd/p/000000084.000068334.html)）
- 発案者（ゆう）は、祖父母が介護施設に入居していた家族として、この「様子が分からない不安」と「電話のしにくさ」を実際に経験している

#### 既存のサービスの課題

| サービス | 家族とのやりとり | 課題 |
|---|---|---|
| ケア記録アプリ（介護サプリ）の家族連携 | 施設 → 家族の一方通行（家族は LINE で記録を見るだけ） | 家族は聞きたいことを聞けない |
| Contact Book、ケアコラボ | 双方向（家族がチャット・コメントできる） | 家族からの連絡を職員が全件読んで返すので、職員の負担が増える |

既存のサービスが一方通行に留めている理由は、「双方向にすると職員の負担が増える」ことにある。
このアプリは、**家族の知りたいことに応えながら、職員の負担は増やさない**ことを目指す。

### 3. 目的・ゴール（Goals / Objectives）

#### このプロダクトで達成したいこと（Constitution 原則 I・II）

1. **家族が、日々の様子と知りたいことを、聞かずに・遠慮せずに知れる**
   - 頼まなくても、施設が開示した日々の様子（食事・機嫌・眠り）が連絡帳で見られる
   - 知りたいことは、ボタンで頼めて、職員の返事が連絡帳のいちばん上に届く
2. **職員の入力負担を増やさない**
   - 記録はボタンで 3 タップ以内。家族への返事は定型文のボタンで答えられる
   - 家族からの頼みごとは、職員に通知・音で知らせず、ケアを中断させない
   - 問い合わせは AI が一次対応し、人が対応すべきものだけを、質問の種類を付けて職員に渡す（だれが対応するかは職員が決める。苦情は生活相談員・施設長だけ）
3. **安心して導入できる**：家族に何を見せるかは施設が選ぶ。AI は医療判断をしない（Constitution 原則 III・IV）

#### KPI

各 spec の成功基準（SC-）から、ゴールに直結するものを KPI にする。開発の期間（実装は 7 日間）では、テストシナリオとデモで確かめる。

| KPI | 目標 | spec |
|---|---|---|
| 職員 1 人が 1 食分を記録する時間 | 10 秒以内・3 タップ以内 | spec 001 SC-003 |
| 職員が「知りたいこと」に返事をする時間 | 30 秒以内・3 タップ以内 | spec 001 SC-007 |
| 非開示の記録が家族に見えてしまった件数 | 0 件 | spec 001 SC-006 |
| 職員の記録・返事が、家族に届くまでの時間 | 5 分以内（連絡帳への反映・返事のお知らせ） | spec 001 SC-008・SC-010 |

- 立替金の精算、逆・連絡帳、話すだけで記録、聞き書き AI、難しい質問の下準備、入居前ヒアリング支援 AI（Constitution 原則 V）

- 家族が職員に自由な文章を送る機能（自由な質問は問い合わせ AI（F）で受ける）
- 急変・事故の連絡（これまでどおり施設が電話で知らせる。Constitution 原則 III）
- 複数の施設への対応（施設は 1 つ）
- ネイティブアプリ（今回は作らない。Constitution の課題要件では +α として作ってもよい）
- Web Push（通知はアプリ内のお知らせとメール）

### 6. ユーザーストーリー（User Stories）

- 家族（佐藤さん）として、**頼まなくても今日の食事・機嫌・眠りを連絡帳で見たい**。なぜなら、忙しい施設に電話して聞くのは気が引けるから
- 家族として、**気になることをボタンで頼み、職員の返事を受け取りたい**。なぜなら、文章を考えたり電話したりせずに、聞きたいことを聞けるから
- 家族として、**AI に質問して、記録をもとにすぐ答えてほしい**。人が答えるべきことは、施設の職員につないでほしい。なぜなら、ちょっとしたことで職員の手を止めたくないから
- 家族として、**面会の空いている時間を見て、アプリで予約したい**。なぜなら、電話で日時を調整する手間をなくしたいから
- 介護職員（田中さん）として、**お世話の場で、ボタンを押すだけで記録したい**。なぜなら、IT が苦手で、記録に時間をかけたくないから
- 介護職員として、**家族の頼みごとに、ケアの合間に定型文のボタンで返事をしたい**。なぜなら、ケア中に電話で呼ばれたくないから
- 家族として、**母の日々の様子や行事を、写真で見たい**。なぜなら、文字の記録だけでは、楽しそうにしているか、行事の雰囲気がどうかがわからないから
- 介護職員として、**写真を撮って載せるだけで、家族に様子を伝えたい**。なぜなら、文章よりも手軽に、入居者の表情や様子が伝わるから
- 外国人の介護職員（シティさん）として、**母国語でメモを書き、整った日本語で家族に届けたい**。なぜなら、日本語の記録に時間がかかるから
- 生活相談員（山本さん）として、**人が対応すべき問い合わせだけを受けたい**。家族に何を見せるかを項目ごとに決めたい。なぜなら、問い合わせが集中して業務が止まるから
- 事務員（佐々木さん）として、**施設からのお知らせ（毎月の献立表を含む）を、アプリで全家族に届けたい**。なぜなら、紙や電話での連絡の手間を減らしたいから
- 施設長（猪熊さん）として、**アプリの利用料をカードで申し込み、契約の状態を確かめたい**。なぜなら、書類や振込の手間なく導入したいから

各ストーリーの受け入れ条件は、spec の User Story・受け入れシナリオを見る。

### 8. 非機能要件（Non-functional Requirements）

#### パフォーマンス
- 職員の記録・返事が、家族の連絡帳に 5 分以内に反映される（画面を開いたときに最新を読む）
- 返事・施設からのお知らせ・面会のお知らせは、5 分以内にアプリ内のお知らせとメールで届く
- 規模は施設 1 つ・入居者 30 人・職員 16 人・家族アカウント 30

#### セキュリティ・個人情報
- 入居者の記録・写真は要配慮個人情報として扱う。通信は https。デモ・開発は架空のデータだけを使う
- 家族は、自分の家族（入居者）の情報だけを見られる。入居者は、ログイン中の家族から決め、送られてきた値では決めない
- 家族に出す記録・テーマ・返事は、必ず共通の関数を通して、施設が開示したものだけにする（AI も同じ）
- XSS 対策（利用者の入力は文字としてだけ表示）、SQL インジェクション対策（ORM でパラメータ化）
- アップロードしたファイルは公開 URL を持たず、ログインと役割を確かめてから返す。画像の位置情報（Exif）は消す
- メール・通知の文面に、記録や返事の中身・入居者名を入れない
- プロンプトインジェクション対策：利用者の入力は AI への命令ではなくデータとして扱い、AI が読める記録を開示された範囲に限る
- カード情報はアプリで受け取らず、決済サービスの画面だけで入力する
- ログは開発と本番で出し方を分け、本番のログに個人情報を出さない
- 決まった時刻の処理を外から呼ぶ専用の API（9 章の案 A）は、環境変数に置いた長い合言葉（トークン）がないと動かないようにし、ログに合言葉を出さない（外から呼べる新しい入口になるため）

#### 対応ブラウザ・OS
- 家族：スマートフォンのブラウザ（iPhone の Safari、Android の Chrome）
- 職員：施設のタブレットのブラウザ
- **（決定）対応するブラウザの版**：**iOS・iPadOS 16.4 以降の Safari、Chrome・Edge 111 以降（Android・PC）、Firefox 128 以降**。
  理由：フロントで使う Tailwind CSS v4 が、これより古いブラウザでは動かない（[Tailwind CSS の動作条件](https://tailwindcss.com/docs/compatibility)）。
  Web アプリなので OS の版ではなくブラウザの版で決める。2023 年 3 月以降に更新されたスマートフォン・タブレットなら、ほぼ当てはまる
- 開発環境：macOS・Windows（Docker Desktop）

#### 使いやすさ・多言語
- 画面を日本語・インドネシア語・英語で切り替えられる。日本語は、固定の文言のすべての漢字にふりがなを付ける

### 9. 技術要件（Tech Requirements）

詳しくは [技術選定](./技術選定.md) を見る。

| 領域 | 使用技術 |
|---|---|
| フロントエンド | React（Vite）・TypeScript、React Router、TanStack Query、Tailwind CSS、react-i18next |
| バックエンド | Python ＋ FastAPI、SQLAlchemy、Alembic |
| データ・キャッシュ | PostgreSQL、Redis（セッション・開示設定のキャッシュ・AI の問い合わせ回数の制限） |
| AI | OpenRouter（学校配布の API キー）＋ OpenAI SDK のツール呼び出し（フレームワークは使わず、ループを自前で書く） |
| 決済 | Stripe Billing（テストモード） |
| 通知 | アプリ内のお知らせ ＋ メール（開発は Mailpit） |
| 環境・本番 | Docker / Docker Compose。本番は Render（https、独自ドメインのサブドメイン） |
| テスト | pytest、Vitest、Playwright（E2E） |

#### 外部サービスとの連携
- OpenRouter（AI。学校配布のキー、使えるモデルは 5 つ）
- Stripe（決済。テストモードで実課金はしない）
- メール送信サービス（本番。開発は Mailpit）
  - **（決定）本番で使うサービスは Resend**。無料プランで 1 日 100 通・月 3,000 通まで送れ、送信に使うドメインは 1 つ（[Resend の料金](https://resend.com/pricing)）。
    デモの規模（家族 30 人に、1 日 1 回のまとめと返事のお知らせ）なら無料プランに収まる。ADVANCE で取得するドメインを、送信元に使う。
  - **（決定）本番のメールの送り方と、決まった時刻の処理（メールの送り直し・20 時のまとめ・前日の面会の知らせ）の動かし方は、案 A（無料のまま）**。
    前提：本番を置く Render の無料のプランでは、SMTP のポート（25・465・587）への外向きの通信が塞がれ（[Render の changelog](https://render.com/changelog/free-web-services-will-no-longer-allow-outbound-traffic-to-smtp-ports)）、
    常に動き続ける worker もなく、使われないと 15 分でスリープする（PR #28 ようこ）。

    | 案 | 中身 | 良いところ・気になるところ |
    |---|---|---|
    | **A：無料のまま（採用）** | 本番は Resend の **API（https）** で送り、開発は今のまま Mailpit に SMTP で送る（環境変数で切り替え）。外部のスケジューラー（cron-job.org）が、合言葉（トークン）付きの専用の API（`POST /api/internal/jobs/run`）を **1 分ごと**に呼び、呼ばれたときに処理する。返事・お知らせのメールは、保存したあとにその場でも送ってみる（送れなければアウトボックスに残り、次に呼ばれたときに送り直す） | お金がかからない。spec 001 の research.md R-09・R-13 を作り替える必要がある。1 分ごとに呼ぶので、「5 分以内に届く」（SC-010）を守れ、サーバーもスリープしない（PR #34） |
    | B：有料にする（採らない） | Render の有料のプラン（Background Worker は月 7 ドルから）で、spec 001 の R-09・R-13 のまま worker で動かす。メールは Resend | 今の設計をそのまま使える。お金がかかる |

    案 A に決定した（PR #28）。spec 001 の research.md R-09・R-13 と、001-T057（さとこ）・本番デプロイ（ようこ）は、これに合わせて直す（R-09・R-13 を直す PR は、ようこの PR #34）

本番デプロイ・プロンプトインジェクション対策・フロントのテスト自動化・サブドメイン・https（ADVANCE）は、[技術選定](./技術選定.md) と Constitution の「課題要件」で対応を決めている。

### 11. リスクと懸念点（Risks & Concerns）

| リスク | 対応 |
|---|---|
| 作る機能が多く、実装の 7 日間（10/22〜10/30）に収まらない | まず Day 4（10/27）までに全機能のミニマム版を作り、そこから作り込む。各機能を優先度（P1〜P5）の順に作り、遅れたら作り込みを削る |
| 学校配布のモデルは小型で、日本語の質やツールを正しく選べるかに差がある | 問い合わせの例を 10 件ほど用意して全モデルで比べ、エージェント用・要約用を決める |
| AI が記録にないことを推測で答える、医療的な判断をする | 記録にないこと・医療・服薬・体調の解釈は、AI が答えずに職員に渡す。AI が読めるのは開示された記録だけ（Constitution 原則 III・IV） |
| 共有の AI のキーの上限を、テストやバグで使い切る | 自動テストでは AI をモックにする。エージェントのループに上限回数、Redis で問い合わせ回数を制限 |
| 非開示の記録や、ほかの家族の情報が見えてしまう | 家族に出すものは共通の関数を通す。入居者はログイン中の家族から決める。全画面を確かめるテストを書く |
| 面会予約が同時に入って、上限を超える | DB の決まり（排他制約・一意制約）と、その日だけの順番待ちで守る（spec 003） |
| 外国人職員の記録を AI で翻訳・整文すると、意味が変わる | 本人が訳し戻しで確かめ、リーダーが承認してから家族に届ける（Constitution 原則 III） |
| 家族が新しいアプリを使ってくれるか（LINE で十分と思われる） | ホームを開くと返事がいちばん上に出るなど、短時間で知りたいことが分かる画面にする |
| 実際の施設・家族からのフィードバックが得られにくい | 発案者の家族としての経験と、民間の調査（背景の 66.6%）などの調べた情報をもとにする |
| 文書（spec・plan・技術選定）どうしが食い違う | 決まったことは議事録とストック文書の両方に書き、PR のレビューで食い違いを確かめる |
